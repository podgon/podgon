# Клиент (Kotlin Multiplatform: Android, позже iOS)

## Стек
Первый релиз — Android; код пишется в `commonMain` (KMP), чтобы iOS добавлялся отдельным этапом (этап 11 плана) без переписывания. Принято владельцем проекта (ADR-004).

| Область | Выбор |
|---|---|
| Язык | Kotlin (актуальная стабильная версия), Coroutines + Flow |
| UI | Compose Multiplatform (Material 3), навигация — Navigation Compose для CMP |
| Архитектура | UDF/MVI: UI → ViewModel (androidx lifecycle-viewmodel KMP) → UseCase → Repository → DataSource |
| DI | Koin (KMP-совместимый) |
| Сеть | Ktor Client + kotlinx.serialization (модели и ошибки — из `shared-contract`, клиент — из OpenAPI) |
| Локальные данные | Room KMP или SQLDelight (кэш), DataStore (настройки), токены — платформенное защищённое хранилище (`expect/actual`: Android Keystore / iOS Keychain) |
| Пагинация | Paging KMP (androidx.paging), keyset по cursor |
| Платформенное | deep links (App Links / Universal Links), push (FCM, позже), открытие почтового клиента |
| Тесты | kotlin.test, Turbine, MockK/Mokkery, Ktor MockEngine, Compose UI Test |
| Качество | ktlint/Detekt, Android Lint, R8 |
| Сборка | Gradle (Kotlin DSL), version catalog, convention plugins |

Выбор библиотек на KMP-аналоги (Koin, Ktor, Room KMP/SQLDelight) вместо Hilt/Retrofit — сознательное следствие решения о KMP. Перед началом этапа 3 проверяем актуальные стабильные версии.
minSdk — 26 (Android 8.0, на согласование), targetSdk — актуальный требуемый магазином.

## Структура модулей

```
shared-contract/                общие с сервером модели, валидация, коды ошибок (KMP)
mobile/
├── shared/                     KMP (commonMain + androidMain + iosMain)
│   ├── core/{common,model,network,database,datastore,designsystem,ui}
│   └── feature/{auth,profile,groups,categories,reviews,search}
├── androidApp/                 точка входа Android, манифест, подпись
└── iosApp/                     (этап 11) точка входа iOS
```
В каждом feature: `ui/` (Screen, ViewModel, State, Event), `domain/` (UseCase, интерфейсы), `data/` (репозитории, мапперы). `domain`/`model` — чистый Kotlin. Платформенный код — только через `expect/actual` или интерфейсы с реализациями в `androidMain`/`iosMain`.

## Навигация и экраны

- Вне авторизации: Приветствие → Ввод email (+ CAPTCHA) → Ввод кода из письма (с повторной отправкой и кнопкой «открыть почту») → для нового пользователя: username и displayName → вход. Пароля и его восстановления нет.
- После входа: нижняя навигация — **Лента** (все группы с переключателем группы), **Поиск**, **Группы**, **Профиль**.
- Лента: карточки рекомендаций (название, оценка, категория, теги, автор с ролью, группа), фильтры (категории деревом, теги, автор), pull-to-refresh, бесконечная прокрутка.
- Карточка рекомендации: полное описание, действия автора (редактировать/удалить/изменить группы).
- Создание/редактирование: название, описание, оценка (1–10), выбор групп → категория для каждой группы (с подстановкой по шаблону) → теги (ввод с `#`, автодополнение из тегов группы).
- Группы: список, создание, экран группы (участники с ролями, категории, приглашения, настройки), вступление по приглашению (deep link / ввод кода) с экраном выбора, чем поделиться (все / категории / подкатегории / теги / кроме… / ничего) и предпросмотром количества. Записи без соответствия категории в новой группе (по `template_id`) показываются отдельным списком: для каждой можно выбрать категорию вручную или отказаться от переноса.
- Выход из группы: диалог с опцией «удалить мои отзывы в группе»; для единственного администратора выход недоступен с пояснением (назначить другого админа или удалить группу).
- Удаление группы: диалог с количеством отзывов, существующих только в группе, и выбором «вернуть авторам в личные» / «удалить» (второй — с явным подтверждением).
- Личные рекомендации: раздел «Мои», видимый только автору; при создании группы выбираются явно, последний выбор подсказывается.
- Профиль: имя, displayName, bio, активные сессии (устройства) с возможностью завершить, выход, удаление аккаунта (подтверждение кодом из письма; чекбокс «удалить также все мои отзывы» — по умолчанию выключен; показывается количество отзывов, в том числе опубликованных в группах, и предупреждение, что без чекбокса они останутся анонимно у «Удалённого пользователя»).
- Удаление категории: диалог с предупреждением и подтверждением; при наличии отзывов — дополнительное предупреждение, что отзывы будут удалены (данные берутся из `delete-impact`).
- Скрытие админ-действий для обычных участников (но сервер — источник правды по правам).

## Состояние и данные
- UDF/MVI: `UiState` (immutable), `UiEvent` (разовые эффекты), `Action`. `StateFlow` + `collectAsStateWithLifecycle`.
- Репозитории возвращают `Flow`; единый тип результата (`Success/Error`) с типизированными ошибками, маппингом `problem+json` → доменные ошибки → локализованные сообщения.
- Кэш: Room как источник правды для ленты и групп (single source of truth), сеть обновляет кэш; офлайн — чтение, правки только онлайн (YAGNI).
- Токены: `AuthInterceptor` добавляет access; `Authenticator` OkHttp на 401 выполняет refresh (с мьютексом против гонок); при провале refresh — выход на экран входа.
- Состояние UI и ввода переживает поворот/убийство процесса (`SavedStateHandle`).

## Безопасность клиента
- Только HTTPS; `network-security-config` без cleartext (исключение для debug-эмулятора), опциональный pinning.
- Токены в Keystore-защищённом хранилище; `allowBackup=false` или исключение секретов из бэкапа.
- Нет логирования чувствительных данных (HttpLoggingInterceptor только в debug и с маскированием `Authorization`).
- Поле кода — `oneTimeCode` autofill (Android: SMS/email autofill по возможности), без логирования кода.
- R8 + обфускация, подписание Play App Signing.
- Play Integrity не используется как обязательный (нет на устройствах без сервисов Google).
- CAPTCHA на регистрации — Яндекс SmartCaptcha через WebView/SDK.
- Никаких обязательных зависимостей от сервисов Google и зарубежных SDK (аналитика, краш-репорты, шрифты, карты) — приложение должно работать из РФ без VPN и на устройствах без GMS (ADR-010). Базовый URL API настраивается (возможность смены при блокировке).

## Требования магазинов (Google Play; закладываем заранее)
- Канал распространения — Google Play (аккаунт разработчика на Узбекистан), запасной — прямой APK с сайта. RuStore — отдельный поздний этап 12 плана (после iOS). Приложение бесплатное.
- Push: FCM (в бэклоге; из РФ работает нестабильно, на работу приложения не влияет — push не критичен).
- Подписанный AAB, актуальный `targetSdk`, Data safety форма, политика конфиденциальности (URL).
- Удаление аккаунта внутри приложения + веб-страница для запроса удаления.
- UGC-политика: жалоба на контент, блокировка пользователя.
- Правильная работа с разрешениями (минимум; на старте их нет, кроме INTERNET).
- Доступность (TalkBack, размеры шрифта, контраст), тёмная тема, адаптивность (телефон/планшет).
- Локализация: русский и английский, строки в ресурсах (Compose Multiplatform resources), язык по умолчанию — язык устройства, переключатель в профиле.
- Для iOS в будущем: KMP-общий слой (`core/model`, domain, часть data), UI на SwiftUI или Compose Multiplatform.

## Платформенные особенности
- Android: App Links, Keystore, FCM; iOS (позже): Universal Links, Keychain, APNs, правила App Store (в т. ч. удаление аккаунта в приложении).

## Тестирование
- Unit: UseCase, ViewModel (Turbine), мапперы, валидаторы (username, теги, оценка).
- Интеграционные: репозитории с MockWebServer + in-memory Room.
- UI: Compose-тесты ключевых экранов (вход, создание рекомендации, фильтры).
- E2E (по возможности): сценарий против docker-compose бэкенда в CI.

## Согласованность с сервером и БД
- Клиент использует код, сгенерированный из `api/openapi.yaml`; правила валидации (длины, формат username, теги, оценка 1–10) берутся из контракта и дублируются в UI только для UX — сервер остаётся источником правды.
- Коды ошибок API — единый перечень, сопоставленный со строковыми ресурсами.

## Предложения и обоснования
- **Compose вместо View-системы:** современный стандарт, меньше кода, лучше тестируемость.
- **Мультимодульность с первого дня:** ускоряет сборку и обеспечивает границы; сложность умеренная благодаря convention plugins. Допустимо начать с `app` + `core` + `feature` без излишнего дробления.
- **Приглашения как App Links** (`https://podgon.app/invite/<token>`): удобно делиться, при отсутствии приложения — страница-заглушка со ссылкой на магазин. Нужна верификация домена (assetlinks.json).
- **Ввод кода подтверждения email** внутри приложения предпочтительнее ссылки из письма (меньше проблем с deep link и антифрод); ссылка — запасной вариант.
