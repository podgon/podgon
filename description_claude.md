# Какую реализацию выбрал бы Claude, имея только функциональное описание

Гипотетический вариант: если бы в `description.md` не было раздела про стек (Android, Java, Postgres) и оставалось только то, что приложение должно делать.
Он не заменяет принятую архитектуру (см. [architecture.md](architecture.md)), а показывает, где бы я пошёл другим путём и почему.

## Что в задаче определяет выбор
- Это приложение вокруг данных: ленты, фильтры, поиск, группы и права. Тяжёлых вычислений, реального времени и медиа почти нет.
- Закрытая аудитория, нагрузка скромная. Главные риски — корректность прав доступа (утечка между группами) и скорость разработки, а не масштабирование.
- Отзывы читают чаще, чем пишут, и им не нужен офлайн-режим.

## Мой выбор

| Область | Выбор | Почему |
|---|---|---|
| Клиент | **Kotlin Multiplatform + Compose Multiplatform** (Android и iOS из одной кодовой базы) | Приложение состоит из форм, списков и фильтров, то есть стандартного UI. Один код на две платформы вдвое дешевле. Kotlin и Compose стабильны, а нативные API при необходимости доступны. Альтернатива — Flutter, но KMP лучше стыкуется с JVM-сервером |
| Веб | **Не делать на старте**, позже — PWA или тонкий веб-клиент | Задача мобильная, а веб расширяет охват, но не нужен для проверки идеи |
| Сервер | **Kotlin + Spring Boot** (или Ktor) на JVM LTS, модульный монолит | Общий язык с клиентом, общие модели и валидация. Spring даёт зрелую безопасность и экосистему. Ktor — легче, но Spring лучше по Security и привычен команде |
| БД | **PostgreSQL** | Полнотекстовый поиск на русском, иерархии (рекурсивные CTE) и транзакции закрывают все потребности без отдельной поисковой системы |
| Контракт | **OpenAPI, contract-first**, генерация клиента и сервера | Рассинхрон частей — главный источник ошибок в проектах такой формы |
| Авторизация | Email + одноразовый код (**passwordless**), а пароль опционален | Меньше угроз (нет хранения паролей и перебора), проще UX, меньше кода. Пароль стоит оставить, только если он явно нужен |
| Хостинг | **Управляемые сервисы**: контейнер (Cloud Run / Fly.io / Yandex Serverless Containers) + managed Postgres + CDN/WAF | Нет администрирования серверов, бэкапы и TLS «из коробки» |
| Почта и антибот | Транзакционная почта (Postmark / SES) + Cloudflare Turnstile + rate limit на периметре | Дёшево, закрывает фейковые регистрации |

## Где мой выбор отличается от принятой архитектуры
1. **Kotlin на сервере вместо Java.** Один язык и общий код (модели, валидация) снижают рассинхрон. В `description.md` указан Java-стек, поэтому в проекте оставлена Java.
2. **KMP вместо чистого Android.** Принятая архитектура готовит такую возможность (чистые Kotlin-модули domain и data), но реализует только Android.
3. **Passwordless вместо пароля.** Принятая архитектура сохраняет пароль и Argon2id, потому что описание требует смену пароля и защиту от перебора.
4. **Меньше инфраструктуры.** Без Redis, брокера и Kubernetes. Принятая архитектура тоже придерживается этого (YAGNI).

## Что осталось бы без изменений
- Модульный монолит с жёсткими границами модулей.
- Видимость данных через связь «рекомендация ↔ группа», где категория хранится на связи (ADR-007).
- Единая точка проверки членства в группе и тесты на утечки между группами.
- Миграции Flyway, Testcontainers, CI, защищённые ветки `main` и `stable`.
- Модерация (жалобы и блокировки) с самого начала, потому что магазины требуют её для пользовательского контента.
