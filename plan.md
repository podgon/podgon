# План реализации

Следует процессу из description.md. Каждый этап включает вертикальный срез: **контракт API → БД (миграция) → сервер → клиент → тесты**, чтобы части системы менялись согласованно.

## Процесс этапа (чек-лист для каждого этапа)
1. Проверить, не повлияли ли изменения прошлых этапов на план этого; при необходимости скорректировать и согласовать.
2. Обновить контракт `api/openapi.yaml`, миграции БД.
3. Реализация (сервер, клиент) в ветке `feature/<этап>-...` от `develop`.
4. Тесты, ручное тестирование.
5. Code review, устранение замечаний, повторное тестирование.
6. Документирование кода (комментарии на русском), обновление `*.md`.
7. Merge в `develop`. Merge в `stable` — только через MR и по явному запросу разрешения; `main` — релиз через MR ревьюера.
8. Переход к следующему этапу.

## Этап 0. Согласование и подготовка
- Согласовать архитектуру и открытые вопросы (architecture.md §8), выбрать хостинг, почтового провайдера, вариант антибот-защиты.
- Структура монорепозитория, защита веток `main`/`stable`, шаблон MR, CI-скелет, линтеры.
- **DoD:** открытые вопросы закрыты или явно отложены; ветки защищены; CI зелёный на пустых проектах; решения оформлены ADR.

## Этап 1. Каркас бэкенда и БД
- Spring Boot проект, модули-пустышки, Spring Modulith-проверки, профили, конфигурация через env.
- PostgreSQL + Flyway, начальная миграция (расширения `citext`, `pg_trgm`), Testcontainers.
- Dockerfile, docker-compose (backend + Postgres + Mailpit), Actuator health, единый формат ошибок (RFC 9457 Problem Details), UTF-8 везде.
- **DoD:** `docker compose up` поднимает систему; `/actuator/health` = UP; интеграционный тест с реальным Postgres проходит в CI; миграции применяются с нуля.

## Этап 2. Пользователи и аутентификация (сервер)
- Регистрация, подтверждение email, вход, refresh с ротацией, выход, смена пароля, восстановление пароля, профиль (displayName, bio, username).
- Argon2id, rate limit, блокировки, CAPTCHA-интеграция (за интерфейсом), outbox писем.
- **DoD:** все сценарии покрыты интеграционными тестами, включая негативные (перебор, повторное использование refresh, истёкший код); пароли не попадают в логи; OpenAPI опубликован; ревью безопасности пройдено.

## Этап 3. Каркас Android-клиента и авторизация
- Мультимодульный проект, тема Material 3, навигация, DI (Hilt), сетевой слой, безопасное хранилище токенов, автообновление токена.
- Экраны: регистрация, подтверждение, вход, восстановление пароля, профиль.
- **DoD:** сквозной сценарий «регистрация → подтверждение → вход → выход» работает против сервера в docker-compose; UI/unit-тесты ViewModel; нет cleartext-трафика.

## Этап 4. Группы, участники, роли, приглашения
- Создание группы (создатель = администратор), приглашения (email/ссылка), вступление, удаление участников, назначение администраторов, кастомные роли, инвариант «минимум один админ».
- Клиент: список групп, экран группы, участники, управление ролями, приглашения.
- **DoD:** права проверяются на сервере (тесты на чужие группы); инварианты защищены и ограничениями БД/транзакциями; сценарии работают в клиенте.

## Этап 5. Категории
- Базовый набор категорий (seed-шаблон), копирование в группу при создании, иерархия, создание/удаление администратором, предупреждения при удалении, правила удаления пустой категории / категории только с отзывами инициатора.
- Клиент: дерево категорий, диалоги подтверждения.
- **DoD:** корректные каскады; тест на глубокую иерархию и циклы (цикл запрещён); подтверждения в UI.

## Этап 6. Рекомендации
- CRUD рекомендаций, оценка 1–10, теги, публикация в группы с категорией для каждой группы, лента группы с keyset-пагинацией.
- Клиент: лента, карточка, форма создания/редактирования (выбор групп/категорий/тегов), локальный кэш (Room).
- **DoD:** автор управляет только своим; участники видят только опубликованное в своих группах; нагрузочный smoke на ленту (индексы подтверждены `EXPLAIN`).

## Этап 7. Поиск и фильтры
- Полнотекстовый поиск (русская морфология) + trigram по названию; фильтры по категориям (с потомками), тегам, автору, их комбинации.
- Клиент: поиск, панель фильтров, сохранение последнего фильтра.
- **DoD:** релевантный поиск на тестовом наборе; фильтры комбинируются; производительность на ~100k рекомендаций приемлема (целевой p95 < 300 мс).

## Этап 8. Шаринг при вступлении, выход из группы, удаление аккаунта
- Правила «поделиться»: все / категории / подкатегории / теги / кроме категорий / кроме тегов / ничего (с предпросмотром количества).
- Выход из группы (опционально с удалением своих публикаций в ней), мягкое удаление аккаунта (анонимизация, отзыв токенов), веб-страница удаления аккаунта для Google Play.
- **DoD:** все варианты правил покрыты тестами; выход/удаление не нарушают инварианты групп; данные удалённого пользователя недоступны.

## Этап 9. Модерация и подготовка к публикации
- Жалобы на контент/пользователей, блокировка пользователя, политика конфиденциальности и условия использования.
- Play Integrity, финальные лимиты, R8/ProGuard, подписание AAB, Data safety форма, иконки/скриншоты, закрытое тестирование в Google Play.
- **DoD:** пройдена предрелизная проверка Google Play Console; нет блокирующих замечаний; security-review пройден.

## Этап 10. Релиз и эксплуатация
- Прод-окружение, бэкапы и проверка восстановления, мониторинг и алерты, runbook, нагрузочное тестирование, релиз `main`.
- **DoD:** задеплоено в прод, бэкап восстановлен на тест, алерты настроены, документация эксплуатации готова.

## Backlog (после первой версии)
Push-уведомления (FCM), фото в рекомендациях, лайки/комментарии, избранное, iOS (KMP), вход через Google, вынос поиска в отдельный сервис.

## Риски
| Риск | Митигирование |
|---|---|
| Сложная модель «категория группы ↔ рекомендация в нескольких группах» | Решение зафиксировано в ADR-007; рано проверяется на этапе 6 |
| Спам-регистрации | Многоуровневая защита, инвайты |
| Требования Google Play к UGC | Модерация на этапе 9, заложена архитектурно |
| Задержки доставки писем | Outbox + выбор надёжного провайдера |
