# Клиент (Kotlin Multiplatform: Android, позже iOS)

## Стек
Первый релиз — Android; код пишется в `commonMain` (KMP), чтобы iOS добавлялся отдельным этапом (этап 11 плана) без переписывания. Принято владельцем проекта (ADR-004).

| Область | Выбор |
|---|---|
| Язык | Kotlin (актуальная стабильная версия), Coroutines + Flow |
| UI | Compose Multiplatform (Material 3), навигация — Navigation Compose для CMP |
| Архитектура | UDF/MVI: UI → ViewModel (androidx lifecycle-viewmodel KMP) → UseCase → Repository → DataSource |
| DI | Koin (KMP-совместимый) |
| Сеть | Ktor Client + kotlinx.serialization (модели и ошибки — из `shared-contract`, клиент — из OpenAPI) |
| Локальные данные | Room KMP (кэш, реализовано на этапе 6), DataStore (настройки), токены — платформенное защищённое хранилище (`expect/actual`: Android Keystore / iOS Keychain) |
| Пагинация | Paging KMP (androidx.paging), keyset по cursor |
| Платформенное | deep links (App Links / Universal Links), push (FCM, позже), открытие почтового клиента |
| Тесты | kotlin.test, Turbine, MockK/Mokkery, Ktor MockEngine, Compose UI Test |
| Качество | ktlint (Detekt — после стабильного релиза 2.0), Android Lint, R8 |
| Сборка | Gradle (Kotlin DSL), version catalog, convention plugins |

Выбор библиотек на KMP-аналоги (Koin, Ktor, Room KMP/SQLDelight) вместо Hilt/Retrofit — сознательное следствие решения о KMP. Перед началом этапа 3 проверяем актуальные стабильные версии.
minSdk — 26 (Android 8.0, на согласование), targetSdk — актуальный требуемый магазином.

## Структура модулей

```
shared-contract/                общие с сервером модели, валидация, коды ошибок (KMP)
mobile/
├── shared/                     KMP (commonMain + androidMain + iosMain)
│   ├── core/{common,model,network,database,datastore,designsystem,ui}
│   └── feature/{auth,profile,groups,categories,reviews,search}
├── androidApp/                 точка входа Android, манифест, подпись
└── iosApp/                     (этап 11) точка входа iOS
```
В каждом feature: `ui/` (Screen, ViewModel, State, Event), `domain/` (UseCase, интерфейсы), `data/` (репозитории, мапперы). `domain`/`model` — чистый Kotlin. Платформенный код — только через `expect/actual` или интерфейсы с реализациями в `androidMain`/`iosMain`.

## Навигация и экраны

- Вне авторизации: Приветствие → Ввод email (+ CAPTCHA) → Ввод кода из письма (с повторной отправкой и кнопкой «открыть почту») → для нового пользователя: username и displayName → вход. Пароля и его восстановления нет.
- После входа: нижняя навигация — **Лента** (все группы с переключателем группы), **Поиск**, **Группы**, **Профиль**.
- Лента: карточки рекомендаций (название, оценка, категория, теги, автор с ролью, группа), фильтры (категории деревом, теги, автор), pull-to-refresh, бесконечная прокрутка.
- Карточка рекомендации: полное описание, действия автора (редактировать/удалить/изменить группы).
- Создание/редактирование: название, описание, оценка (1–10), выбор групп → категория для каждой группы (с подстановкой по шаблону) → теги (ввод с `#`, автодополнение из тегов группы).
- Группы: список, создание, экран группы (участники с ролями, категории, приглашения, настройки), вступление по приглашению (deep link / ввод кода) с экраном выбора, чем поделиться (все / категории / подкатегории / теги / кроме… / ничего) и предпросмотром количества. Записи без соответствия категории в новой группе (по `template_id`) показываются отдельным списком: для каждой можно выбрать категорию вручную или отказаться от переноса.
- Выход из группы: диалог с опцией «удалить мои отзывы в группе»; для единственного администратора выход недоступен с пояснением (назначить другого админа или удалить группу).
- Удаление группы: диалог с количеством отзывов, существующих только в группе, и выбором «вернуть авторам в личные» / «удалить» (второй — с явным подтверждением).
- Личные рекомендации: раздел «Мои», видимый только автору; при создании группы выбираются явно, последний выбор подсказывается.
- Профиль: имя, displayName, bio, активные сессии (устройства) с возможностью завершить, выход, удаление аккаунта (подтверждение кодом из письма; чекбокс «удалить также все мои отзывы» — по умолчанию выключен; показывается количество отзывов, в том числе опубликованных в группах, и предупреждение, что без чекбокса они останутся анонимно у «Удалённого пользователя»).
- Удаление категории: диалог с предупреждением и подтверждением; при наличии отзывов — дополнительное предупреждение, что отзывы будут удалены (данные берутся из `delete-impact`).
- Скрытие админ-действий для обычных участников (но сервер — источник правды по правам).

## Состояние и данные
- UDF/MVI: `UiState` (immutable), `UiEvent` (разовые эффекты), `Action`. `StateFlow` + `collectAsStateWithLifecycle`.
- Репозитории возвращают `Flow`; единый тип результата (`Success/Error`) с типизированными ошибками, маппингом `problem+json` → доменные ошибки → локализованные сообщения.
- Кэш: Room как источник правды для ленты и групп (single source of truth), сеть обновляет кэш; офлайн — чтение, правки только онлайн (YAGNI).
- Токены: `AuthInterceptor` добавляет access; `Authenticator` OkHttp на 401 выполняет refresh (с мьютексом против гонок); при провале refresh — выход на экран входа.
- Состояние UI и ввода переживает поворот/убийство процесса (`SavedStateHandle`).

## Безопасность клиента
- Только HTTPS; `network-security-config` без cleartext (исключение для debug-эмулятора), опциональный pinning.
- Токены в Keystore-защищённом хранилище; `allowBackup=false` или исключение секретов из бэкапа.
- Нет логирования чувствительных данных (HttpLoggingInterceptor только в debug и с маскированием `Authorization`).
- Поле кода — `oneTimeCode` autofill (Android: SMS/email autofill по возможности), без логирования кода.
- R8 + обфускация, подписание Play App Signing.
- Play Integrity не используется как обязательный (нет на устройствах без сервисов Google).
- CAPTCHA на регистрации — Яндекс SmartCaptcha через WebView/SDK.
- Никаких обязательных зависимостей от сервисов Google и зарубежных SDK (аналитика, краш-репорты, шрифты, карты) — приложение должно работать из РФ без VPN и на устройствах без GMS (ADR-010). Базовый URL API настраивается (возможность смены при блокировке).

## Требования магазинов (Google Play; закладываем заранее)
- Канал распространения — Google Play (аккаунт разработчика на Узбекистан), запасной — прямой APK с сайта. RuStore — отдельный поздний этап 12 плана (после iOS). Приложение бесплатное.
- Push: FCM (в бэклоге; из РФ работает нестабильно, на работу приложения не влияет — push не критичен).
- Подписанный AAB, актуальный `targetSdk`, Data safety форма, политика конфиденциальности (URL).
- Удаление аккаунта внутри приложения + веб-страница для запроса удаления.
- UGC-политика: жалоба на контент, блокировка пользователя.
- Правильная работа с разрешениями (минимум; на старте их нет, кроме INTERNET).
- Доступность (TalkBack, размеры шрифта, контраст), тёмная тема, адаптивность (телефон/планшет).
- Локализация: русский и английский, строки в ресурсах (Compose Multiplatform resources), язык по умолчанию — язык устройства, переключатель в профиле.
- Для iOS в будущем: KMP-общий слой (`core/model`, domain, часть data), UI на SwiftUI или Compose Multiplatform.

## Платформенные особенности
- Android: App Links, Keystore, FCM; iOS (позже): Universal Links, Keychain, APNs, правила App Store (в т. ч. удаление аккаунта в приложении).

## Тестирование
- Unit: UseCase, ViewModel (Turbine), мапперы, валидаторы (username, теги, оценка).
- Интеграционные: репозитории с MockWebServer + in-memory Room.
- UI: Compose-тесты ключевых экранов (вход, создание рекомендации, фильтры).
- E2E (по возможности): сценарий против docker-compose бэкенда в CI.

## Согласованность с сервером и БД
- Клиент использует код, сгенерированный из `api/openapi.yaml`; правила валидации (длины, формат username, теги, оценка 1–10) берутся из контракта и дублируются в UI только для UX — сервер остаётся источником правды.
- Коды ошибок API — единый перечень, сопоставленный со строковыми ресурсами.

## Предложения и обоснования
- **Compose вместо View-системы:** современный стандарт, меньше кода, лучше тестируемость.
- **Мультимодульность с первого дня:** ускоряет сборку и обеспечивает границы; сложность умеренная благодаря convention plugins. Допустимо начать с `app` + `core` + `feature` без излишнего дробления.
- **Приглашения как App Links** (`https://podgon.app/invite/<token>`): удобно делиться, при отсутствии приложения — страница-заглушка со ссылкой на магазин. Нужна верификация домена (assetlinks.json).
- **Ввод кода подтверждения email** внутри приложения предпочтительнее ссылки из письма (меньше проблем с deep link и антифрод); ссылка — запасной вариант.

## Реализация этапа 3 (факты и отклонения от первоначального плана)
- **Стек и версии:** Kotlin 2.3.21, AGP 9.4.1 (встроенный Kotlin, KMP-библиотеки через `com.android.kotlin.multiplatform.library`), Compose Multiplatform 1.12.2 + Material 3 1.9.0, Ktor 3.6.0 (OkHttp-движок на Android), kotlinx.serialization 1.12.0, Koin 4.2.2, androidx lifecycle-viewmodel 2.11.0 и navigation-compose 2.10.0 (JetBrains KMP-сборки). `compileSdk` 37 (требуют OkHttp 5.5/lifecycle), `targetSdk` 36, `minSdk` 26.
- **Сетевой слой — вручную, не генерацией:** контракт `api/openapi.yaml` ведётся вручную, DTO общие (`shared-contract`, `@Serializable`), клиент `AuthApi`/`MeApi` на Ktor написан руками. Расхождения с контрактом ловят тесты сервера (они сверяют ответы с yaml) и клиентские тесты на `MockEngine`. Генерация клиента отклонена: два набора моделей и тяжёлая сборка при малом числе эндпоинтов; вернёмся к вопросу, если эндпоинтов станет много.
- **Модули:** `shared-contract` (общий с сервером), `mobile:shared` (core: `error`, `network`, `auth`; feature: `auth`, `profile`; `designsystem`; `di`; `App`), `mobile:androidApp`. Разбиение `core/*` и `feature/*` на отдельные Gradle-модули отложено до появления нескольких фич (YAGNI): границы пока выдерживаются пакетами.
- **Токены:** `SessionManager` — единая точка правды (состояние `Loading/SignedOut/SignedIn`, мьютекс); на Android токены шифруются AES-256-GCM ключом Android Keystore (`AndroidTokenStorage`). Ktor `Auth/bearer`: на 401 один раз обновляет пару через `/auth/refresh` (публичный клиент), при отказе refresh — выход. Токен не отправляется на `/api/v1/auth/*`.
- **Ошибки:** `AppError` (`Network`, `Api(status, code, fieldErrors, retryAfterSeconds)`, `Unknown`); неизвестные коды ошибок не ломают разбор. Тексты — только на клиенте (ресурсы ru/en, Compose Resources).
- **Безопасность:** `usesCleartextTraffic` выключен; HTTP разрешён только в debug для `10.0.2.2`/`localhost` (`src/debug/res/xml/network_security_config.xml`); `allowBackup=false`, исключение данных из переноса; в логи ничего не пишется. Адрес API задаётся сборкой (`podgon.debugApiBaseUrl`, `podgon.apiBaseUrl`); адрес продакшена пока заглушка `https://api.podgon.invalid`.
- **CAPTCHA:** интерфейс `CaptchaProvider` есть, реализация-заглушка возвращает `null`; виджет SmartCaptcha (WebView) подключается на этапе 9 вместе с включением проверки на сервере (в dev-окружении `PODGON_CAPTCHA_MODE=disabled`).
- **Тесты:** 22 unit-теста (`MockEngine`, Turbine, тестовый диспетчер): репозиторий входа, ViewModel'и (email, код с автопроверкой и таймером повтора, регистрация), refresh и отсутствие токена на публичных эндпоинтах. Сквозной тест `EndToEndTest` (`androidHostTest`) гоняет реальный клиентский стек против живого сервера (email → код из письма → регистрация → профиль → автообновление токена → выход); запускается при `PODGON_E2E_API` и `PODGON_E2E_MAIL_FILE`, в CI пропускается.
- **Не сделано в этапе 3:** автоматизированная проверка iOS-таргета — на машине разработчика нет Xcode (проверена только компиляция общего кода в metadata); UI-тесты Compose и запуск на эмуляторе/устройстве (нет системных образов Android); R8/подпись — этап 9.

### iOS-таргеты (проверка совместимости, этап 3)
- Таргеты `iosArm64` и `iosSimulatorArm64` в `shared-contract` и `mobile/shared`; фреймворк `PodgonShared` (static). Для образа backend таргеты и Android отключены флагом `-PserverOnly`.
- `iosMain`: Keychain (`IosTokenStorage`, `AfterFirstUnlockThisDeviceOnly`), Ktor Darwin, `DeviceInfoProvider` через `UIDevice`, точка входа `mainViewController(apiBaseUrl)` для будущего `iosApp` (этап 11).
- Kotlin обновлён до 2.4.21: `kotlinx-serialization 1.12.0` собрана Kotlin 2.4.10, и Kotlin/Native 2.3 её не читает.
- Проверено на Xcode 27.1 и симуляторе iOS 27.1: те же unit-тесты клиента проходят на iOS. Имена тестов без запятых и двоеточий (ограничение Native).
- Сам `iosApp` (Xcode-проект), Universal Links, CI на macOS — этап 11.

### Реализация этапа 8 (шаринг, выход, удаление группы и аккаунта)
- `JoinGroupViewModel`: после предпросмотра группы — выбор правила переноса (`ShareMode`: ничего / все / из категорий / кроме категорий / с тегами / кроме тегов, флаг «с подкатегориями»); категории берутся из всех своих групп, теги вводятся строкой. Предпросмотр (`POST /invitations/share-preview`) пересчитывается при каждом изменении правила, для тегов — по IME «Готово» или кнопке. Записи без категории в новой группе показаны списком с выбором категории или «Не переносить»; в `accept` уходят только назначения для записей из предпросмотра.
- `GroupViewModel`: перед выходом и удалением загружает последствия (`leave-impact`, `delete-impact`); диалоги `LeaveGroupDialog` (флажок «Убрать и мои публикации») и `DeleteGroupDialog` (судьба рекомендаций только этой группы: остаются личными / удаляются).
- `ProfileViewModel` + `DeleteAccountDialog`: последствия, флажок «удалить все мои рекомендации», код на почту, подтверждение; группы единственного админа показываются и блокируют удаление. После успеха закрывается локальная сессия (`AuthRepository.accountDeleted`).
- Проверено на телефоне: вступление с правилом «все» и ручным назначением (итог на сервере: 2 автоматически + 1 вручную), выход с удалением публикаций, удаление группы, удаление аккаунта кодом из письма (аккаунт анонимизирован, группа из одного участника удалена). Остальные правила (категории, теги) покрыты тестами ViewModel и сервера.

### Реализация этапа 7 (поиск и фильтры)
- `FeedViewModel` работает с областью `FeedScope` (группа, мои рекомендации, все группы) и фильтром `ReviewFilter` (строка поиска, категории, теги + режим «все/любой», автор). В ленте группы — строка поиска (действие «Найти» на клавиатуре), кнопка «Фильтры (N)» и «Сбросить»; панель фильтров (диалог) подгружает категории (деревом, с подкатегориями), теги группы со счётчиками и участников при первом открытии. Экран «Поиск» (кнопка на списке групп) ищет по всем своим группам и подписывает карточки названием группы.
- Последний фильтр группы запоминается в локальном кэше (`filter:<groupId>`) и восстанавливается при следующем открытии; при выходе из аккаунта очищается вместе с кэшем. Результаты с фильтром не кэшируются (офлайн показывается только пустой фильтр), следующие страницы идут по курсору с теми же параметрами.
- Проверено на телефоне: поиск (в том числе с опечаткой), фильтр по двум тегам, запоминание фильтра, поиск по всем группам. Категории и автора в панели проверены тестами; кириллицу `adb` вводить не умеет, поэтому тестовые данные латиницей.

### Реализация этапа 6 (рекомендации, срезы 6a–6b)
- `feature/reviews`: `FeedViewModel` (лента группы либо «мои рекомендации», подгрузка страниц по курсору кнопкой «Показать ещё»), `ReviewViewModel` (карточка; правка и удаление — только автору), `ReviewFormViewModel` (создание/правка: название, описание, оценка слайдером 1–10, теги одной строкой через пробел, группы флажками с выбором категории для каждой; публикации задаются вместе с созданием, при правке — `PATCH` + `PUT .../groups`). Входы: кнопка «Рекомендации» на странице группы и «Мои рекомендации» на списке групп.
- Проверено на телефоне: валидация формы, создание с публикацией, лента группы, «Мои рекомендации», удаление с подтверждением. Правка проверена только тестами ViewModel.
- **Локальный кэш (срез 6c):** выбран Room KMP 2.8.5 + KSP 2.3.12 + `sqlite-bundled` 2.6.2 (совместимы с Kotlin 2.4.21 и AGP 9.4 с KMP-плагином; обработчик Room подключён для каждой цели через `kspAndroid`/`kspIosArm64`/`kspIosSimulatorArm64`, схемы — `mobile/shared/schemas`). Таблица `cached_response(key, json, savedAt)`: ключи `feed:<groupId>`, `mine`, `review:<id>`. `ReviewsRepository` читает с сервера и сохраняет первую страницу каждой ленты и открытые карточки; при **сетевой** ошибке (не при 404/403!) отдаёт сохранённое с пометкой «Нет сети», следующие страницы из кэша не берутся, правка и удаление офлайн недоступны. Кэш очищается при любом выходе (`SessionManager.onSignOut`) и при смене схемы пересоздаётся. Данные в кэше — JSON-блобы, а не нормализованные таблицы (YAGNI; поиск и фильтры этапа 7 работают на сервере). Android проверен на телефоне (список и карточка без сети после перезапуска приложения), iOS — тест DAO на симуляторе (`CacheDatabaseTest`).
- Не сделано: нижняя навигация, роль автора в карточке ленты, подстановка категории по шаблону.

### Реализация этапа 5 (категории)
- `feature/groups`: `CategoriesViewModel` (плоский список с сервера → дерево обходом в глубину, `flattenTree`/`subtreeIds`) и `CategoriesScreen`: дерево с отступами; администратору по нажатию на категорию открывается диалог действий (отдельные кнопки в каждой строке не помещались на узком экране): создание подкатегории, изменение, перенос (диалог выбора родителя без самой категории и её потомков) и удаление с диалогом подтверждения по данным `delete-impact`; создание в корне — кнопка «Новая категория». Проверено на телефоне (шаблон, подкатегория, перенос, каскадное удаление). Участник видит дерево без кнопок изменения. Ошибки `CATEGORY_*` локализованы.

### Реализация этапа 4 (группы)
- `feature/groups`: ViewModel и экраны — список групп (главный экран после входа; профиль открывается кнопкой), создание группы, вступление по коду (ввод → предпросмотр → подтверждение), страница группы (участники; для админа — смена роли, удаление участника, роли, приглашения; выход из группы; удаление группы), роли (создание, изменение, удаление), приглашения (по коду или на email; токен показывается один раз в диалоге и копируется системным жестом выделения).
- Встроенные роли ADMIN и MEMBER сервер называет по-русски; клиент показывает их локализованными по коду (`RoleInfo.displayTitle()`).
- Подтверждения для необратимых действий (выход, удаление группы, удаление участника, удаление роли) — диалоги; ошибки `LAST_ADMIN`, `INVALID_INVITATION`, `ALREADY_MEMBER`, `LIMIT_EXCEEDED` и др. локализованы.
- Откладено: системное меню «Поделиться» и ссылки-приглашения (Universal/App Links) — этап 9–11; кнопка «Назад» на iOS — вместе с iosApp (этап 11).
