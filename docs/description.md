# Podgon
## Краткое описание проекта
Подгон -- это приложение для обмена рекомендациями (отзывами) внутри закрытой группы людей.
Рекомендации могут быть любыми: книга, фильм, выставка, ресторан, гид, служба доставки еды, мастер по ремонту. 
Основная идея в том, что человек получает не просто рекомендации и отзывы от незнакомых людей в интернете, которые могут быть проплачены, а от людей с похожими взглядами, чьему мнению он доверяет.
## Описание реализации
### Краткое описание
Система будет представлять из себя современное мобильное приложение для Android + бэкенд + БД.
Все используемые библиотеки и фреймворки должны быть свободно распространяемыми, стабильных актуальных версий и с большим опытом применения в реальных проектах.
### Стек и технологии
* Приложение для Android должно быть написано на современном Kotlin
* Backend должен использовать Java-стек на LTS версии
* СУБД должна быть бесплатной и достаточно производительной, например, Postgres
* При проектировании архитектуры можно с обоснованием предложить альтернативы вышеупомянутому стеку с обоснованием
### Базовые принципы 
* Любая реализация следует описанному ниже плану (см. Этапы реализации).
* Использование Best practice в разрезе используемых инструментов.
* Использование уместных шаблонов проектирования и реализации.
* Изменения в каждой из частей (клиент, бэкенд, БД) должны быть согласованы и не противоречить друг другу.
* Разумное следование принципам Clean code, SOLID, DRY, YAGNI, KISS. Допустимо обоснованное отступление от принципов там, где это улучшит реализацию.
* Использование ветвления git для разделения системы в разрезе стабильности: main (production), stable (production-ready), develop (develop).
* Артефакты, обсуждения, комментарии в коде: на русском языке.
* Push в main и stable только через MR. MR принимает только ревьюер (человек).
### Этапы реализации
* Архитектурное проектирование, ADR и план реализации с этапами
* Определение definition of done каждого этапа
* Согласование и обсуждение открытых вопросов
* Поэтапная реализация согласно плану:
  * Проверка, не повлияли ли изменения в реализации предыдущих этапов на план реализации данного
  * Изменение и согласование реализации данного этапа (при необходимости, см. пред. пункт) 
  * Реализация этапа
  * Реализация тестов (если предусмотрены этапом)
  * Тестирование
  * Code review
  * Устранение замечаний code review (при наличии)
  * Изменение тестов и повторное тестирование (при необходимости, если после ревью были правки кода)
  * Документирование кода и комментарии
  * Merge в stable при успешных тестах и приемке (всегда только по согласованию с явным запросом разрешения)
  * Переход к следующему этапу
### Детали реализации
#### Код
* Код на одном языке должен быть написан в едином стиле
* При написании кода нужно использовать общепринятые конвенции стиля и наименований для соответствующего языка
* Новый код должен быть написан с учетом уже существующего (переиспользование, согласованность)
### Архитектура
* Начальная реализация должна быть монолитом, но структура должна учитывать возможный переход к микросервисам в будущем
* При проектировании бэкенда необходимо предусмотреть возможность запуска в контейнере
* Код мобильного приложения должен учитывать необходимость публикации данного приложения в соответствующем магазине приложений (для Android - Google Play, для iOS - AppStore)
### Детали
* Вход в систему доступен только авторизоаваным пользователям. Авторизация по email с подтверждением
* Должна быть защита от искусственной автоматической генерации аккаунтов и ddos (эта защита может быть реализована хостингом/облачным провайдером). Предложить варианты на этапе проектирования.
* Должна быть защита от sql-инъекций
* Везде сразу используется utf-8 для избежания проблем с кодировками
* Для процедуры логина пользователя должны быть предусмотрены стандартные средства защиты: защита от перехвата учетных данных, защита от перебора пароля, надёжное шифрованное хранение пароля и тд
### Сущности системы
**Набор изложенных ниже сущностей, их полей и способа связей служит для базового представления структуры. Он может быть дополнен/изменен на этапе проектирования, конструктивные предолжения приветствуются**
* Рекомендация (отзыв) -- основная сущность, представляет собой отзыв или рекомендацию на товар, услугу, событие и т.д. 
Состоит из названия, описания, оценки (1 - 10), категории (ссылка), подкатегории (должна соответствовать иерархии категорий), тегов (несколько, начинаются c #, будут использоваться при фильтрации), пользователя-автора (ссылка), набор групп (ссылка на несколько), даты и времени создания.
* Группа -- служит для объединения пользователей, рекомендации которых будут видны друг другу. Пользователь видит только рекомендации внутри групп, в которых он состоит, и которыми другие участники группы поделились с этой группой.
Состоит из наименования, ссылки на сводную таблицу пользователей группы (один пользователь может принадлежать нескольким группам; в группе может быть несколько пользователей),
ссылки на сводную таблицу отзывов, принадлежащих группе (один отзыв пользователя может быть в нескольких группах одновременно), ссылка на набор категорий группы
* Категория - категория, к которой относится отзыв. Используется для фильтрации, поддерживает иерархию (Например, Страны -> Албания). Отдельно хранится базовый набор категорий, который по умолчанию добавляется каждой группе при создании.
Администратор группы может добавлять и удалять категории в своей группе. Возможно удаление пустой категории или категории, где все отзывы оставлены пользователем, который инициирует удаление.
При удалении категории должно выдаваться предупреждение пользователю с подтверждением. если в категории есть отзывы, должно быть так же предупреждение, что отзывы удалятся вместе с категорией.
Состоит из наименования, описания, ссылки на пользователя-создателя, даты и времени создания, ссылки на группу, ссылки на родительскую категорию.
* Пользователь - пользователь системы, который создает отзывы и группы. Может иметь базовую роль или роль администратора группы. Создатель группы по-умолчанию становится её администратором, группа не может существовать без администратора.
Администратор может назначать других пользователей группы её администраторами.
Состав полей: email регистрации пользователя (обязательное, уникальное), имя пользователя (обязательное уникальное до 30 символов, без пробелов и др лишних знаков, которые обычно не используются в пользовательских именах), роль пользователя, отображаемое имя (произвольное до 60 символов), bio (текст до 120 символов)
* Роль пользователя - базовые роли это администратор группы и базовый пользователь (без роли). Так же администратор может создавать кастомные роли в группе. Наименование роли отображается рядом с именем пользователя (как сделано в Группах Telegram, например).
Состав полей: код роли, описание, признак администратора, принадлежность группе (кастомную роль можно назначить только внутри группы, которой она принадлежит)
### Возможности системы
**Набор изложенных ниже возможностей служит для базового представления функционала. Он может быть дополнен/изменен на этапе проектирования, конструктивные предложения приветствуются**
* Пользователь может:
  * Авторизовываться в системе
  * Изменять свой пароль и данные о себе (кроме email регистрации)
  * Создавать / редактировать / удалять собственные отзывы отзывы
  * Создавать группы
  * Создавать кастомные категории и теги внутри своей группы
  * Вступать в группы по приглашению их администраторов
  * Администрировать группы (приглашать / удалять пользователей, назначать роли, создавать / редактировать / удалять кастомные роли), при наличии роли администратора
  * Искать рекомендации, принадлежащие группам, в которых он состоит по описанию
  * Фильтровать рекомендации в группах, в которых он состоит, по одной или по набору категорий, по одному или нескольким тегам, по автору, по совокупности этих фильтров
  * Иметь возможность при вступлении в новую группу выбрать, какими из уже существующих рекомендаций поделиться с новой группой (все, конкретные категории, подкатегории, конкретные теги, кроме конкретных категорий, кроме конкретных тегов, никакие)
  * Покинуть группу. При выходе из группы должна быть возможность удалить все свои отзывы в этой группе (становятся недоступными для группы)
  * Удалить свою учетную запись (на самом деле запись помечается как удаленная)
* Пользователь не может:
  * Иметь доступ к системе без авторизации
  * Выполнять действия, на которые у него нет прав
  * Иметь прямой доступ к базе данных и другим стратегическим объектам и настройкам системы
