# Ревью архитектуры после этапов 0–8

Дата: 2026-10-26, состояние `develop` на коммите `b116f74`. Просмотрены `docs/*.md`; ключевые утверждения сверены с кодом (`server/`, `mobile/`, `.github/`).
Замечания, которые не входят в план этапа 9, вынесены в отдельный этап плана — **8.1 «Замечания по review первых 8 этапов»** (`plan.md`).

## Общая оценка

Архитектура для проекта такого масштаба выбрана удачно. Сильные стороны:

- **Модульный монолит + Spring Modulith** с проверкой границ тестами — правильный старт без преждевременных микросервисов.
- **`shared-contract` + тесты, сверяющие запросы и ответы с `openapi.yaml`** — согласованность клиента, сервера и контракта проверяется автоматически.
- **Модель «рекомендация + публикация» (ADR-007)** с категорией на связи `review_groups` — верное решение самой сложной части предметной области. Составные FK `(category_id, group_id)` и `(role_id, group_id)` гарантируют принадлежность к группе на уровне БД.
- **Инвариант «≥ 1 админ»**: блокировка в сервисе + отложенный триггер в БД, проверено тестом на гонку.
- **Вход без пароля**: HMAC кодов, ротация refresh с отзывом цепочки, одинаковый ответ, outbox — модель угроз описана честно.
- **ADR-010 (работа из РФ без VPN)** — ограничение среды оформлено как архитектурный драйвер.
- Keyset-пагинация и подтверждённая `EXPLAIN` и замерами производительность поиска на 100 тыс. записей.

Слабые места: документация разошлась с кодом, часть границ модулей существует только на бумаге, не хватает нескольких обязательных для мобильного приложения механизмов.

## Важно (до первой публикации)

**R1. Нет механизма принудительного обновления клиента.** Нет передачи версии клиента (`X-Client-Version`) и ответа «обновите приложение» (426 или машинный код ошибки). Контракт ещё 0.x; после релиза любое несовместимое изменение сломает старые APK без понятного сообщения. Закладывается **до первой публикации** — потом старые версии о механизме не узнают.

**R2. Смена адреса API при блокировке не спроектирована.** ADR-010 обещает «запасной домен и смену базового URL», но адрес задаётся только сборкой. Минимум — зашитый в приложение список из 2–3 доменов с переключением при сетевых ошибках; конфигурация с сервера (подписанная) — позже.

**R3. Блокировка, удаление и отзыв сессии действуют не сразу.** Access-токен живёт 15 минут, статус пользователя и сессии на запросе не проверяется (`SecurityConfig`). Для модерации (этап 9) это означает, что заблокированный нарушитель ещё 15 минут может публиковать. Дешёвое решение — проверка статуса пользователя/сессии по PK на каждом запросе (при текущем масштабе бесплатно); альтернатива — TTL 5 минут.

**R4. IP для лимитов за прокси.** `forward-headers-strategy: none` по умолчанию. Если за Caddy/Nginx не включить настройку — все пользователи получат IP прокси, и лимит «20 кодов в час на IP» заблокирует вход для всех. Если включить без ограничения доверенных прокси — лимит обходится подделкой `X-Forwarded-For`. Нужны тест и пункт runbook.

**R5. Нет лимитов для авторизованных запросов.** В `server.md` заявлены Bucket4j и «общий лимит на пользователя», в коде лимиты есть только у входа, групп и приглашений. Самый дорогой запрос — поиск с триграммами — не ограничен. Минимум — `limit_req` на reverse proxy, лучше — ещё и лимит на пользователя в приложении.

**R6. Миграции под ролью приложения.** `db.md` обещает разделение `podgon_app` (без DDL) и `podgon_migrator`; сейчас Flyway работает при старте под пользователем приложения, у которого, следовательно, есть DDL. Нужен отдельный пользователь Flyway (`spring.flyway.user`) или миграции отдельным шагом деплоя.

## Документация разошлась с кодом

**R7.** Будущий участник проекта будет опираться на документ, а не на код:

| Документ | Написано | В коде |
|---|---|---|
| `server.md`, стек | Spring Data JPA/Hibernate, `kotlin-jpa`, Bucket4j, Spring Security 6 | `JdbcClient` без JPA, Bucket4j нет; версия Security — та, что идёт со Spring Boot 4 |
| ADR-001, `server.md` | модули `search`, `notifications`, пакет `api` | поиск внутри `reviews`, публичные порты — в корне пакета модуля |
| ADR-005, `client.md` | DTO и клиент генерируются из OpenAPI, проверка совместимости `oasdiff` в CI | клиент написан вручную (решение этапа 3); `oasdiff` в CI нет — только комментарий-заглушка |
| `server.md`, сценарий 8 | `DELETE /me?deleteReviews=…` | `POST /me/deletion` |
| `client.md` | OkHttp `Authenticator`, Paging KMP, Room как единый источник правды, нижняя навигация | Ktor `Auth`, кнопка «Показать ещё», кэш JSON-блобами, нижней навигации нет |
| `architecture.md` §8 | модерация — этап 8 | по плану — этап 9 |
| `architecture.md` §5 | JSON-логи, Prometheus-метрики | зависимостей `micrometer-registry-prometheus` и JSON-логирования нет |

Предложение: привести ADR и разделы «Стек» к факту; отменённые решения не стирать, а помечать «Заменено решением этапа N».

## Границы модулей

**R8. `reviews` ↔ `catalog` — фактически циклическая связь.** SQL модуля `reviews` читает таблицу `categories` (рекурсивные CTE в `ReviewRepository`, `SharingRepository`, подбор по `template_id`), а `catalog` зависит от порта `reviews.ReviewPublications`; между таблицами — FK. Spring Modulith видит зависимости только в коде, не в SQL, поэтому заявленная готовность к выделению сервисов для этой пары не соответствует действительности. Варианты: **(рекомендуется)** признать категории и рекомендации одним ограниченным контекстом (модуль «контент»); либо явно записать в ADR-001 допущение «чтение таблиц соседнего модуля» со списком мест.

**R9. Синхронные события с `@Order` в одной транзакции.** `MemberJoined`, `UserDeleting` и др. обрабатываются в транзакции публикующего модуля в заданном порядке — удобно и атомарно, но это межмодульная распределённая транзакция. Менять сейчас не нужно; в ADR-001 записать: «межмодульные инварианты держатся на общей транзакции; при выделении модуля — Event Publication Registry Spring Modulith и компенсации».

## Мелкие замечания и предложения

- **R10. UUIDv7.** PostgreSQL 18 умеет `uuidv7()`; для новых таблиц с интенсивной записью — лучшая локальность индексов. Существующие таблицы не трогать.
- **R11. «ё» в поиске.** Словарь `russian` не приравнивает «ё» к «е» («ёлка» ≠ «елка»). Нормализовать в генерируемой колонке (`translate`) или через `unaccent` (собран в локальном PostgreSQL). Английский текст в конфигурации `russian` обрабатывается нормально (`english_stem` для латиницы).
- **R12. Словарь `tags` только растёт** — неиспользуемые теги не удаляются; чистка по расписанию.
- **R13. Код входа в открытом виде в `mail_outbox.payload`** — осознанный компромисс (стирается после отправки), но может попасть в бэкап; TTL 10 минут делает риск малым. Записать в модель угроз.
- **R14. Клиентский кэш после исключения из группы.** Кэш ленты группы остаётся до выхода из аккаунта и офлайн показывает данные группы, к которой доступа уже нет. Удалять `feed:<groupId>` при 404 и при обновлении списка групп.
- **R15. Detekt** не подключён — проверить, вышел ли стабильный 2.0.
