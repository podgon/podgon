# Архитектура Podgon

Документ описывает общую архитектуру системы, ключевые решения (ADR), сквозные аспекты (безопасность, развёртывание, качество) и открытые вопросы.
Детали подсистем: [client.md](client.md), [server.md](server.md), [db.md](db.md). План работ: [plan.md](plan.md).

## 1. Контекст и цели

Podgon — мобильное приложение для обмена рекомендациями внутри закрытых групп. Ключевая ценность — доверие: пользователь видит только то, чем поделились участники его групп.

Архитектурные драйверы:

| Драйвер | Следствие |
|---|---|
| Закрытость данных (видимость только внутри групп) | Проверка прав на сервере в каждом запросе, единая точка авторизации доступа к данным, тесты на утечки между группами |
| Старт монолитом, возможный переход к микросервисам | Модульный монолит с жёсткими границами модулей |
| Пользователи в РФ работают **без VPN** | Хостинг и все рантайм-зависимости доступны из РФ; нет обращений приложения и сервера к недоступным из РФ сервисам (ADR-010) |
| Запуск в контейнере | Stateless-бэкенд, конфигурация через переменные окружения, 12-factor |
| Публикация в Google Play (позже App Store) | Целевой SDK, подписанные AAB, политика удаления аккаунта, privacy policy; логика отделена от UI для возможного KMP |
| Бесплатные стабильные библиотеки | Только mainstream OSS (Spring, Compose, PostgreSQL и т. п.) |
| Защита от ботов, DDoS, SQL-инъекций, перебора кодов входа | Многоуровневая защита (раздел 6) |
| Русский язык в артефактах и комментариях, UTF-8 везде | Фиксируем в конфигурации БД, JVM, HTTP, сборки |

## 2. Общая схема

```
┌──────────────────────┐        HTTPS (REST/JSON, JWT)        ┌─────────────────────────────┐
│ Android-приложение   │ ───────────────────────────────────▶ │ CDN/WAF/Reverse proxy       │
│ Kotlin + Compose     │                                       │ (TLS, rate limit, anti-bot) │
│ Room (кэш)           │ ◀─────────────────────────────────── │                             │
└──────────────────────┘                                       └──────────────┬──────────────┘
                                                                              ▼
                                                               ┌─────────────────────────────┐
                                                               │ Backend (Spring Boot, Kotlin) │
                                                               │ модульный монолит, контейнер│
                                                               └──────┬───────────────┬──────┘
                                                                      │ JDBC          │ SMTP / API
                                                                      ▼               ▼
                                                            ┌────────────────┐  ┌────────────────┐
                                                            │ PostgreSQL     │  │ Почтовый       │
                                                            │ (Flyway-миграц.)│  │ провайдер      │
                                                            └────────────────┘  └────────────────┘
```

Клиент не имеет прямого доступа к БД: только через API бэкенда. БД доступна только из приватной сети бэкенда.

## 3. Ключевые решения (ADR)

### ADR-001. Модульный монолит
- **Решение:** один деплоймент, внутри — модули с публичным API и скрытой реализацией: `identity` (пользователи, вход, сессии), `groups` (группы, участники, роли, приглашения), `reviews` (рекомендации, теги, публикации, поиск **и категории**), `mail` (outbox писем). Модули `search`, `notifications`, `moderation` из первоначального плана отдельно не создавались: поиск живёт в `reviews`, модерация появится на этапе 9. *Заменено решением этапа 8.1 (R8):* бывший модуль `catalog` (категории) объединён с `reviews`.
- **Обоснование:** требование описания. Модульный монолит дешевле в разработке и эксплуатации, чем микросервисы, но при жёстких границах позволяет вынести модуль позже.
- **Как обеспечиваем границы:** Spring Modulith (тест `ModularityTests`), публичный порт модуля — интерфейсы и события в корне его пакета (например, `groups.GroupAccess`, `identity.UserDirectory`, `mail.MailQueue`), реализация — во внутренних подпакетах. Внешние ключи между таблицами разных модулей оставлены ради целостности (одна БД). **Ограничение проверки:** Modulith видит зависимости только в Kotlin-коде, а не в SQL, поэтому чтение чужих таблиц в запросах проверяется ревью.
- **Категории и рекомендации — один модуль (этап 8.1, R8).** SQL рекомендаций читает дерево категорий (фильтр «с подкатегориями», подбор категории по `template_id` при шаринге), а удаление категории считает публикации — это один ограниченный контекст. Пока они были двумя модулями, связь шла в обход проверок (чтение таблицы `categories` из `reviews`, порт `ReviewPublications` в обратную сторону). Объединение сделано сразу: позже оно дорожало бы с каждой функцией, затрагивающей обе части.
- **Межмодульные инварианты (этап 8.1, R9).** Модули `groups` и `identity` публикуют **синхронные** события (`GroupCreated`, `MemberJoined`, `MemberLeft`, `GroupDeleting`, `UserDeleting`), обработчики в других модулях выполняются в той же транзакции, порядок задан `@Order`. Это даёт атомарность (например, группа не появляется без категорий; удаление аккаунта либо выполняется целиком, либо не выполняется), но по сути это общая транзакция нескольких модулей. При выделении модуля в отдельный сервис такие связи переводятся на асинхронные события через outbox (Event Publication Registry Spring Modulith) с компенсирующими действиями; инварианты, которые сейчас держит общая транзакция, придётся обеспечивать иначе.
- **Альтернатива:** сразу микросервисы — отвергнуто (YAGNI, сложность для команды).

### ADR-002. Backend: Kotlin (JDK 25 LTS) + Spring Boot 4.x
- **Решение принято владельцем проекта.** Kotlin компилируется в JVM-байткод, исполняется на LTS-версии JVM (25; выбрана вместо 21, так как это текущая LTS и она уже установлена в окружении разработки), поэтому остаётся «Java-стеком» в смысле платформы (JVM, Spring, Gradle, JDBC).
- **Обоснование:** единый язык с клиентом (KMP) и общий код: модели, правила валидации (username, теги, оценка 1–10, длины), коды ошибок выносятся в общий модуль `shared-contract` и подключаются и к серверу, и к клиенту — расхождения ловит компилятор. Null-safety, sealed-классы и корутины упрощают код (например, правила шаринга — sealed-иерархия). Spring Boot — де-факто стандарт с зрелыми Security, Data, Validation, Actuator, полная поддержка Kotlin.
- **Нюансы:** плагины `kotlin-spring` и `kotlin-jpa` (JPA-сущности требуют открытых классов и конструктора без аргументов), осторожность с data-классами как JPA-сущностями; общий модуль должен быть чистым Kotlin/JVM+KMP без Spring-зависимостей.
- **Альтернативы:** Ktor (легче, но меньше готового для Security/Data), Java (больше разработчиков на рынке, но нет общего кода с клиентом). Переход на следующую LTS JVM — отдельной задачей. Версия Spring Boot 4.x выбрана как актуальная стабильная (проверено по Maven Central перед этапом 1).
- **Сборка:** Gradle (Kotlin DSL) — единый инструмент для сервера и клиента.

### ADR-003. БД: PostgreSQL 18
- **Обоснование:** бесплатная, производительная, зрелая; нативные возможности, нужные проекту: полнотекстовый поиск (русская морфология), `pg_trgm`, рекурсивные CTE для иерархии категорий, частичные индексы, `citext`, JSONB.
- **Миграции:** Flyway (версионированный SQL, принцип «БД меняется только миграциями»).
- **Поиск:** на первом этапе — встроенный FTS PostgreSQL, без Elasticsearch (YAGNI). Выделение поиска в отдельный модуль даст возможность заменить движок.

### ADR-004. Клиент: Kotlin Multiplatform + Compose Multiplatform
- **Решение принято владельцем проекта.** Общий код (модели, сеть, бизнес-логика, ViewModel, UI) в `commonMain`; платформенные детали (хранилище токенов, deep links, push, уведомления) через `expect/actual` или интерфейсы с платформенными реализациями.
- **Первый релиз — Android** (Google Play); iOS — отдельный этап плана (этап 11), архитектура и зависимости выбираются сразу KMP-совместимыми.
- **Обоснование:** приложение — формы, списки, фильтры, т. е. стандартный UI без нативной специфики; один код вдвое дешевле двух. Общий код с сервером (ADR-002).
- **Ограничения:** экосистема KMP/CMP для iOS моложе; часть библиотек имеет КМР-аналоги вместо Android-версий (Room KMP или SQLDelight, Koin вместо Hilt, Ktor client вместо Retrofit). Для iOS потребуется Mac и Xcode, аккаунт Apple Developer (платный, отдельный вопрос); вопросы публикации в App Store для РФ — отдельно.
- **Альтернативы:** Flutter (отдельный язык, нет общего кода с сервером), нативные Android+iOS (двойная стоимость).

### ADR-005. Протокол: REST/JSON, контракт OpenAPI (contract-first)
- **Обоснование:** простота, поддержка инструментов, кэширование. Единый контракт `openapi.yaml` в репозитории — источник правды для клиента и сервера, что выполняет принцип «изменения согласованы и не противоречат друг другу».
- *Заменено решением этапа 3:* DTO не генерируются — они общие для сервера и клиента в `shared-contract`, клиент на Ktor написан вручную. Расхождения с контрактом ловят серверные тесты (каждый запрос и ответ сверяется с `api/openapi.yaml`) и клиентские тесты на `MockEngine`. Обратную совместимость контракта проверяет `oasdiff` в CI (задание `contract`, этап 8.1).
- Устаревшие сборки клиента отсекаются сервером: клиент передаёт `X-Client-Platform` и `X-Client-Version`, ниже минимальной версии — 426 `UPGRADE_REQUIRED` и экран обновления (этап 8.1, R1).
- **Альтернативы:** GraphQL (избыточно для текущих сценариев), gRPC (хуже для мобильного/отладки). Версионирование через префикс `/api/v1`.

### ADR-006. Аутентификация: passwordless — вход по одноразовому коду из письма
- **Решение принято владельцем проекта.** Пароля в системе нет: вход и регистрация идут по email и одноразовому коду. Это осознанное отступление от `description.md` («изменять свой пароль», «защита от перебора пароля», «шифрованное хранение пароля»): требования к паролю снимаются как неактуальные, их цели достигаются иначе (см. ниже).
- **Сценарий:** пользователь вводит email (+ CAPTCHA) → сервер отправляет 6-значный код (всегда отвечает одинаково, не раскрывая, есть ли аккаунт) → пользователь вводит код → если аккаунт есть, получает токены; если нет — получает короткоживущий `registrationToken` и завершает регистрацию вводом username и displayName. Так подтверждение email — неотъемлемая часть входа, а запись `users` создаётся только после регистрации.
- **Код:** 6 цифр, генерация `SecureRandom`, TTL 10 мин, ≤ 5 попыток ввода, после превышения код аннулируется, повторная отправка не чаще раза в 60 с и ≤ 5 в час на email; в БД хранится только HMAC-SHA256 (с серверным секретом), активен один код на email; сравнение за постоянное время.
- **Токены:** access JWT (15 мин; при каждом запросе дополнительно проверяется, что сессия не отозвана и пользователь активен — выход, отзыв сессии, блокировка и удаление аккаунта действуют сразу, этап 8.1, R3), refresh — непрозрачный случайный токен, в БД только хэш, ротация при каждом использовании, повторное использование → отзыв всей цепочки (token family). Хранение на клиенте в защищённом хранилище платформы (Android Keystore / iOS Keychain). Сессии (устройства) видны пользователю и отзываются вручную (`/me/sessions`) — это замена «смены пароля» при подозрении на компрометацию.
- **Угрозы и защита:** перебор кода → короткий TTL, лимит попыток, rate limit по email и IP, CAPTCHA; спам чужим ящикам запросами кода → лимиты на email/IP/устройство, CAPTCHA, одинаковый ответ; перехват письма/почтового ящика → единственный фактор, поэтому риск полностью зависит от безопасности почты пользователя (принимаем; возможное усиление — второй фактор, в backlog); перехват трафика → только TLS 1.2+, HSTS.
- **Риски passwordless:** зависимость от доставки писем (задержки, спам-папка) — российский почтовый провайдер, SPF/DKIM/DMARC, понятный UX «письмо не пришло» с повторной отправкой, мониторинг доставляемости. Доступность почты для входа критична: при её недоступности вход невозможен, пока не восстановится сервис.
- **Модерация магазинов:** магазинам нужен тестовый аккаунт. Предусматриваем управляемое исключение: для одного выделенного тестового email фиксированный код через конфигурацию; включается флагом, по умолчанию выключен, в продакшене отключается после модерации.
- **Альтернативы:** пароль (отклонено), Sign in with Google/Apple (не снимает обязанностей по ПДн, зависит от сервисов Google/Apple, нестабильно из РФ; VK ID/Яндекс ID не рассматриваем), magic link вместо кода (хуже для мобильных из-за deep link и почтовых клиентов с предзагрузкой ссылок).

### ADR-007. Модель видимости: «рекомендация + публикация в группу»
- Рекомендация принадлежит автору; доступ к ней группе даёт запись «публикации» (`review_group`). Эта связь many-to-many хранит также **категорию рекомендации в рамках этой группы** (категории принадлежат группам, а рекомендация может быть в нескольких группах — прямая ссылка на одну категорию невозможна).
- Выход из группы с удалением отзывов = удаление записей публикаций этого автора в данной группе; сама рекомендация остаётся в других группах.
- Правило безопасности: любой запрос чтения рекомендаций обязан идти через представление «доступные пользователю публикации» (join по членству). Реализуется в одном месте (репозиторий/спецификация), покрывается тестами.
- Подробности и альтернативы: db.md, раздел «Категория рекомендации».

### ADR-008. Мягкое удаление пользователей
- Учётная запись помечается `deleted_at`, email освобождается/анонимизируется (хэш), персональные данные очищаются; отзывы остаются, а их автором становится системный пользователь «Удалённый пользователь» (решение §8, п.1). Требование Google Play: возможность удаления аккаунта внутри приложения и по веб-ссылке.

### ADR-009. Уведомления и почта
- Отправка писем через абстракцию `MailSender`; в разработке — Mailpit/MailHog, в проде — российский провайдер с хорошей доставляемостью на mail.ru/yandex/gmail (Yandex Cloud Postbox, Unisender Go, Mailganer), обязательны SPF, DKIM, DMARC. Отправка асинхронная (outbox-таблица, повтор при сбоях).
- Push — вне первой версии, но модуль `notifications` оставляем под него. FCM из РФ работает нестабильно, поэтому при реализации push используем FCM, но он не должен быть критичен для работы приложения (см. ADR-010).

### ADR-010. Доступность из РФ без VPN
- **Требование:** пользователь в РФ пользуется приложением без VPN. Приоритетнее удобства разработки: GitHub, Maven Central и др. инструменты разработки можно использовать как есть.
- **Решения:**
  1. **Решение: хостинг Selectel (РФ)** для бэкенда и БД; антибот — **Яндекс SmartCaptcha**. Домен — через российского регистратора, DNS у российского провайдера (можно Selectel DNS).
  2. Рантайм-зависимости приложения и сервера — только сервисы, доступные из РФ: SmartCaptcha, российская почта, push (FCM, некритичный). Нет Firebase Analytics/Crashlytics, внешних шрифтов, карт и CDN зарубежных компаний; шрифты и ресурсы — внутри приложения. Краш-репорты — самохостинг (Sentry/GlitchTip) или собственный эндпоинт.
  3. Распространение APK: **Google Play** (позже, этап 12 — дополнительно RuStore; аккаунт разработчика планируется на Узбекистан; скачивание бесплатных приложений в РФ работает; **риск:** Google требует достоверные данные и подтверждение личности/адреса, регистрация на страну, где вы не проживаете, может не пройти проверку или привести к блокировке аккаунта — условия проверить до начала публикации) + прямая загрузка APK (запасной вариант). Приложение бесплатное, платные подписки не рассматриваем.  RuStore сознательно не используется (решение владельца); если аккаунт Google Play не пройдёт проверку, запасной вариант — прямой APK с сайта.
  4. Приложение не должно зависеть от сервисов Google для работы: нет обязательных GMS-API (Play Integrity, FCM), чтобы работало и на устройствах без них.
  5. Периодическая проверка доступности: мониторинг API из РФ (внешний чекер с российских площадок), так как блокировки меняются.
  6. **Запасные адреса API (этап 8.1, R2):** в сборку зашиваются основной и запасные адреса (`podgon.apiFallbackUrls`). При сетевом сбое клиент проверяет запасные (`GET /actuator/health`) и переключается на первый отвечающий до перезапуска приложения; GET повторяется автоматически, изменяющие запросы — только действием пользователя (без риска двойного выполнения). Удалённая конфигурация адресов — по необходимости позже.
- **Риски:** блокировки по IP/SNI хостинга и CDN, нестабильность отдельных зарубежных сервисов. Митигирование: российский хостинг, запасной домен и возможность сменить базовый URL API (удалённая конфигурация/обновление приложения), TLS-сертификаты от доступного в РФ УЦ (Let's Encrypt работает; запасной — российский УЦ).

## 4. Структура репозитория

```
podgon/
├── api/            openapi.yaml — контракт
├── server/         Spring Boot (Gradle)
├── shared-contract/ общий KMP-модуль: модели, правила валидации, коды ошибок (сервер + клиент)
├── mobile/         KMP-клиент: shared (commonMain), androidApp, iosApp (позже)
├── deploy/         Dockerfile, docker-compose, скрипт роли БД (db-init); миграции живут в server/
├── docs/adr/       отдельные ADR по мере появления
└── *.md            описание, архитектура, план
```
Монорепозиторий упрощает согласованность контракта между частями (единый MR меняет API, сервер и клиент).

## 5. Ветвление, CI/CD, качество

- Ветки: `main` (production), `stable` (production-ready), `develop` (разработка). Фичи — `feature/<этап>-<кратко>` от `develop`.
- Push в `main` и `stable` только через MR, принимает человек-ревьюер (защищённые ветки в GitHub). Merge в `stable` — только по явному запросу разрешения.
- CI (GitHub Actions): сборка, unit-/integration-тесты (Testcontainers с PostgreSQL), линтинг (ktlint; статанализ Detekt добавим после стабильного релиза 2.0 — 1.23.x не работает на JDK 25), проверка контракта OpenAPI, сканирование зависимостей (Dependabot, OWASP dependency-check), сборка Docker-образа.
- Тестовая пирамида: unit → интеграционные (API + реальный Postgres в контейнере) → UI-тесты ключевых сценариев на клиенте.
- Соглашения: Kotlin (сервер и клиент) — официальный Kotlin style (ktlint), SQL — snake_case, комментарии и документация на русском.
- Наблюдаемость: структурированные логи (JSON), Actuator health/metrics, Prometheus-совместимые метрики, трассировка запросов через `X-Request-Id`; без персональных данных в логах. **Состояние на этап 8.1:** реализованы только health-пробы и отсутствие ПДн в логах; JSON-логи, метрики Prometheus и краш-репорты — этапы 9–10 (R18).
- CI проверяет обратную совместимость контракта `oasdiff` (задание `contract`).

## 6. Безопасность (сквозные меры)

| Угроза | Меры |
|---|---|
| Доступ без авторизации | Все эндпоинты, кроме `/auth/*` и health, закрыты; deny-by-default в Spring Security |
| Перебор кода входа / спам кодами | Короткий TTL и лимит попыток на код, лимиты по email и IP (счётчики в таблице `email_codes`), CAPTCHA, ограничение частоты повторной отправки, одинаковый ответ независимо от существования email. IP клиента берётся из `X-Forwarded-For` только от доверенного прокси (`PODGON_TRUSTED_PROXIES`, R4) |
| Нагрузка от авторизованных пользователей | Лимит запросов в минуту на пользователя и отдельный, более строгий — на поиск (429 + `Retry-After`, R5; счётчики в памяти, при нескольких инстансах — Redis) + `limit_req` на обратном прокси |
| Одноразовый код в очереди писем | Пока письмо не отправлено, код лежит открытым текстом в `mail_outbox.payload` (иначе его не отправить); после отправки или окончательной ошибки payload стирается. Остаточный риск — код попадёт в резервную копию БД, снятую в эти секунды; он ограничен TTL кода 10 минут и лимитом попыток. Принят осознанно (R13) |
| Автоматическая регистрация | Лимиты по IP/устройству/домену email, CAPTCHA **Яндекс SmartCaptcha** (доступна из РФ; hCaptcha/reCAPTCHA/Turnstile не используем из-за риска недоступности), подтверждение email, запрет одноразовых доменов (опционально), для закрытой группы — вход **по приглашению** как дополнительный фильтр |
| DDoS | Защита на стороне Selectel (услуги защиты от DDoS у провайдера, состав и тариф уточнить при заказе) + rate limit на reverse proxy, лимиты размера запроса и таймауты |
| SQL-инъекции | Только параметризованные запросы (JPA/Spring Data/jOOQ), запрет конкатенации SQL, отдельный пользователь БД с минимальными правами, статанализ |
| Перехват данных | TLS, HSTS, нет cleartext на клиенте |
| Хранение секретов входа | Пароля нет; коды и refresh-токены хранятся только в виде хэша (HMAC-SHA256/SHA-256), секрет-«перец» в окружении |
| Утечка данных между группами | Единая точка проверки членства, интеграционные тесты «чужая группа» → 404/403 |
| IDOR | Идентификаторы UUID + обязательная проверка прав на ресурс |
| XSS/инъекции в тексте отзывов | Текст хранится как plain text; клиент рендерит без HTML; на сервере валидация длины и нормализация |
| Секреты | Только в переменных окружения/секрет-хранилище, не в репозитории |
| Прямой доступ к БД | БД в приватной сети, нет публичного порта, роль приложения `podgon_app` без DDL, миграции — владельцем схемы (R6, `deploy/db-init/app-role.sql`) |

**Минимизация персональных данных.** Полностью избежать ПДн нельзя: email — идентификатор человека, а вход по email требуется описанием. Поэтому принцип — собирать минимум:
- в системе только email, username и необязательные displayName/bio (без реального ФИО, телефона, даты рождения, геолокации, аватаров, контактов);
- никакой сторонней аналитики и рекламных SDK, IP не хранятся дольше окна rate limit, в логах email маскируется;
- email хранится в БД (нужен для приглашений и писем); при удалении аккаунта анонимизируется (ADR-008);
- юридический статус оператора ПДн (152-ФЗ, уведомление Роскомнадзора, политика обработки) всё равно остаётся — уточнить у юриста (вопрос №10).

**Варианты защиты от ботов (для решения на этапе 0):**
1. WAF/CDN хостинга + rate limit на уровне прокси (минимум, бесплатно/дёшево).
2. + CAPTCHA на запросе кода входа (Яндекс SmartCaptcha).
3. + проверка подлинности приложения: Play Integrity API работает только на устройствах с сервисами Google, поэтому как **обязательное** требование не вводим — максимум как дополнительный сигнал риска.
4. + регистрация только по инвайту. **Рекомендация:** 1 + 2 на старте, 4 — как опция группы, 3 — по необходимости.

## 7. Развёртывание

- Образ бэкенда: multi-stage Dockerfile, non-root, слои Spring Boot (layered jar), healthcheck.
- Локально: `docker-compose` (backend + PostgreSQL + Mailpit).
- Прод: **Selectel** (дата-центр в РФ). Старт: облачный сервер (VM) с Docker Compose за reverse proxy (Caddy/Nginx с TLS) + **управляемый PostgreSQL Selectel** с бэкапами; приватная сеть между ними, БД без публичного адреса. Образы — в реестре контейнеров Selectel. Управляемый Kubernetes — только при реальной необходимости (YAGNI). Зарубежные CDN/прокси перед бэкендом не ставим. Для первой версии рекомендуется самый простой вариант: один VPS/контейнерный сервис + managed PostgreSQL.
- Окружения: `dev` (develop), `stage` (stable), `prod` (main).
- Миграции Flyway выполняются при старте (для одного инстанса) либо отдельной задачей деплоя (при нескольких) — под ролью владельца схемы (`PODGON_DB_MIGRATOR_USER`); приложение работает ролью `podgon_app` без DDL (R6).
- Backend наружу не публикуется: только через обратный прокси; адрес прокси задаётся `PODGON_TRUSTED_PROXIES` (R4). Подробности — `deploy/README.md`.

## 8. Предложения по дополнению описания и открытые вопросы

Предложения (**приняты владельцем проекта**; пункты 5 и 7 — в backlog, пункт 6 — этап 9 плана):
1. **Единый реестр категорий группы + «базовый набор» как шаблон:** при создании группы шаблон копируется в категории группы (отслеживается `template_id` для сопоставления между группами).
2. **Приглашения:** по email или по ссылке/коду с TTL и лимитом использований; принятие приглашения — только авторизованным пользователем.
3. **Теги:** нормализуются (нижний регистр, без пробелов, `#` — только в UI), общий словарь тегов; «теги группы» = теги, использованные в публикациях группы. Это проще, чем отдельные теги на группу, и удовлетворяет фильтрации.
4. **Оценка 1–10**, целая; выводить среднее по названию не требуется (YAGNI).
5. **Лайки/комментарии, избранное, «хочу попробовать»** — вне первой версии (backlog).
6. **Модерация:** жалоба на отзыв/пользователя — для публикации в Google Play (UGC-политика) нужна возможность пожаловаться и заблокировать контент/пользователя. **Включено в план — этап 9.**
7. **Фото в рекомендациях** — backlog (потребует объектное хранилище S3-совместимое).

Решения по вопросам (согласованы владельцем проекта):
1. **Удаление аккаунта:** отзывы остаются анонимизированными — автором становится специальный системный пользователь «Удалённый пользователь» (фиксированный `id`, статус `SYSTEM`). Отдельной записи членства в каждой группе не требуется: видимость определяется публикациями (`review_groups`), поэтому системный пользователь «присутствует» во всех группах виртуально и отображается только как автор. Личные отзывы без групп удаляются вместе с аккаунтом (их никто не видит). **Дополнение:** перед удалением аккаунта пользователь может выбрать «удалить также все мои отзывы» — тогда удаляются все его отзывы (включая опубликованные в группах), а не передаются системному пользователю; выбор по умолчанию — не удалять, с явным подтверждением и показом количества.
2. **Личные рекомендации:** рекомендация может существовать без групп и видна только автору.
3. **Публикация при создании:** пользователь выбирает группы явно (последний выбор запоминается как подсказка).
4. **Категория при публикации в несколько групп:** подстановка по `template_id`; при вступлении записи без соответствия переносятся только по явному выбору пользователя (назначить вручную или отказаться).
5. **Правила «поделиться»:** разовое действие, правило не хранится.
6. **Владелец группы:** отдельной роли нет, требование — минимум один администратор.
7. **Выход единственного администратора:** запрещён, пока не назначен другой администратор или группа не удалена.
8. **Удаление группы:** разрешено администратору. Отзывы, опубликованные только в этой группе, администратор обрабатывает выбором: (а) вернуть авторам в личные либо (б) удалить с явным подтверждением (с показом количества). Отзывы, опубликованные и в других группах, остаются в них. Публикации в удаляемой группе удаляются.
9. **Username:** регистронезависимый (`citext`), символы `[a-z0-9_.]`, длина 3–30.
10. **Хостинг:** Selectel (РФ); антибот — Яндекс SmartCaptcha (см. ADR-010).
11. **Офлайн:** чтение закэшированных данных — да, создание и правки — только онлайн.
12. **Языки:** русский и английский. Строки клиента — в ресурсах (`ru`, `en`), коды ошибок API не зависят от языка, письма и названия шаблонных категорий — на двух языках (`users.locale`, `category_template_translations`); язык по умолчанию определяется языком устройства, пользователь может сменить в профиле.

Остаются открытыми (**отложены до завершения локального тестирования, решаются перед публикацией — этап 9**; до тех пор разработка идёт локально: почта — Mailpit, CAPTCHA и внешние сервисы — за интерфейсами с заглушками):
- Почтовый провайдер (Yandex Cloud Postbox / Unisender Go).
- Состав DDoS-защиты и тариф managed PostgreSQL в Selectel.
- Статус оператора ПДн по 152-ФЗ (уточнить у юриста).
- Проходит ли регистрация аккаунта Google Play на Узбекистан для резидента РФ.
