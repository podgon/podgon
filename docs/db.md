# База данных

PostgreSQL 18 (локально установлена 18.6; минимально поддерживаемая — 16), кодировка `UTF8`, `LC_COLLATE`/`LC_CTYPE` — `ru_RU.UTF-8` либо ICU-коллация (`und-x-icu`); все серверные и клиентские соединения в UTF-8. Часовой пояс хранения — UTC (`timestamptz`).
Миграции — Flyway (`V<номер>__<описание>.sql`), правило: применённые миграции не редактируются.
Расширения: `citext`, `pg_trgm`, `pgcrypto` (при необходимости `gen_random_uuid()` встроен с PG13+).

Соглашения: имена `snake_case`, таблицы во множественном числе, PK — `uuid` (генерирует приложение, `UUID.randomUUID()`), у каждой таблицы `created_at timestamptz not null`. **Для новых таблиц с интенсивной вставкой** (журналы, жалобы, события) — UUIDv7 (`uuidv7()` в PostgreSQL 18 или генерация в приложении): хронологический порядок ключей даёт лучшую локальность B-tree индексов. Существующие таблицы не переводятся (этап 8.1, R10).

## ER-диаграмма (логическая)

```
users ──< memberships >── groups (kind: REGULAR | PERSONAL | FAVORITES)
  │            │              │
  │            └── group_roles┘
  │                           │
  └──< reviews ──< review_groups (review, group) >┘
          │  └──> categories (общий набор, self: parent_id) ──< category_names
          └──< review_tags >── tags
groups ──< invitations
users ──< refresh_tokens, reports;  email_codes (по email, без FK)
```

## Таблицы

### users
| Поле | Тип | Ограничения |
|---|---|---|
| id | uuid PK | |
| email | citext | not null, unique (частичный уникальный индекс по `deleted_at is null`) |
| username | citext | not null, unique, `CHECK (username ~ '^[a-z0-9_.]{3,30}$')` |
| display_name | varchar(60) | |
| bio | varchar(120) | |
| status | varchar(16) | `ACTIVE`, `BLOCKED`, `DELETED`, `SYSTEM` (один служебный пользователь «Удалённый пользователь», фиксированный `id`, создаётся миграцией) |
| locale | varchar(5) | `ru` или `en` |
| created_at, updated_at, deleted_at | timestamptz | мягкое удаление |

При удалении: `email` заменяется на `deleted+<id>@invalid` (освобождение адреса), `username` на `deleted_<id>`, `display_name`, `bio` очищаются.

Роль «администратор группы» хранится не в users, а в членстве (роль зависит от группы). Глобальной роли в описании нет; если понадобится глобальный администратор системы (модерация) — отдельное поле `system_role`.

### groups
`id`, `name varchar(100) not null`, `description varchar(500)`, `created_by uuid → users`, `kind varchar(16)`, `created_at`, `updated_at`. Удаление группы физическое (каскад); мягкое удаление не используется (этап 4).

`kind` (этап 8.2.1, V8): `REGULAR` — обычная группа; `PERSONAL` («Личное») и `FAVORITES` («Избранное») — системные группы пользователя `created_by`, по одной каждого вида (частичный уникальный индекс `(created_by, kind) where kind <> 'REGULAR'`). Системные группы создаются при регистрации в одной транзакции с пользователем и удаляются вместе с аккаунтом. Участников и ролей у них нет, поэтому они сами не попадают в список групп, лимит групп, ленту «Все» и управление группой; владелец читает их ленты и теги (проверка по `created_by` и `kind`). Ссылок на них в `users` нет: источник правды — сама группа (отступление от черновика `docs/design.md`, без дублирования данных).

- «Личное»: личные рекомендации автора (Л1). Рекомендация либо личная (публикация только в «Личном»), либо групповая (публикации только в обычных группах).
- «Избранное»: публикация чужой (или своей) рекомендации в своей группе «Избранное». Чужая рекомендация убирается из «Избранного», когда владелец больше не видит её ни в одной своей обычной группе (Ф1: выход, исключение, снятие публикации, удаление группы); при удалении аккаунта автора остаётся — автор становится «Удалённым пользователем» (Ф2). Методы избранного — backlog.

### group_roles
| Поле | Тип | Примечание |
|---|---|---|
| id | uuid PK | |
| group_id | uuid → groups | on delete cascade |
| code | varchar(32) | уникален в пределах группы: `unique(group_id, code)` |
| title | varchar(60) | отображаемое имя роли |
| description | varchar(255) | |
| is_admin | boolean | признак администратора |
| is_system | boolean | системные роли `ADMIN` и `MEMBER` (удалять/редактировать код нельзя) |

Системные роли создаются вместе с группой. Роль «базовый пользователь (без роли)» в БД представлена системной ролью `MEMBER` (чтобы `role_id` был `NOT NULL` и не обрабатывать null); в UI её название не показывается — по аналогии с Telegram. Это отступление от «без роли» ради простоты и целостности (обоснованное).

### memberships (сводная «пользователи ↔ группы»)
`group_id`, `user_id`, `role_id → group_roles`, `joined_at`; PK `(group_id, user_id)`; индекс по `user_id`.
Консистентность «роль принадлежит той же группе»: составной FK `(role_id, group_id) → group_roles (id, group_id)` (в `group_roles` уникальный `(id, group_id)`).
Инвариант «≥ 1 админ в группе» — проверяется в сервисе под блокировкой строки группы; страховка в БД — constraint trigger, откладываемый до конца транзакции (на `memberships` при изменении и удалении и на `group_roles` при смене `is_admin`; пустую группу и удаляемую целиком триггер пропускает). Системные роли ограничены CHECK: ADMIN всегда с правами админа, MEMBER без них, пользовательская роль не может занять эти коды.

### invitations
`id`, `group_id`, `created_by`, `email citext null` (адресное приглашение), `token_hash` (SHA-256, уникальный; токен выдаётся один раз), `expires_at`, `max_uses` (1–100), `used_count` (`CHECK used_count <= max_uses`), `revoked_at`, `created_at`.

### categories и category_names (общий набор, ADR-011)
| Поле | Тип | Примечание |
|---|---|---|
| id | uuid PK | `category_uuid(key)` = `md5('podgon:category:' \|\| key)::uuid` — одинаков во всех базах |
| key | varchar(60) | стабильный ключ из `docs/categories.md` (`books.sf`), unique; не меняется и не переиспользуется |
| parent_id | uuid null → categories | два уровня: корень и подкатегория |
| group_id | uuid null → groups | заготовка под категории групп (вариант К-Б), сейчас всегда `null` |
| sort_order | int | порядок показа |
| system | boolean | «Без категории» (`key = none`) — только для личных рекомендаций |
| archived | boolean | скрыта из выбора; категорию не удаляют, чтобы не ломать старые рекомендации |

Названия — `category_names(category_id, locale, name)`, PK `(category_id, locale)`, языки `ru` и `en`. Набор заполняется миграцией (V8: 21 корень, 218 подкатегорий и «Без категории») и меняется только миграциями. Сервер держит набор в памяти по языку; версия набора — хеш содержимого, она же `ETag` у `GET /categories`.

### review_groups (сводная «отзывы ↔ группы»)
`review_id → reviews (on delete cascade)`, `group_id → groups (on delete cascade)`, `shared_at`; PK `(review_id, group_id)`. Строки — публикации в обычных группах, в «Личном» и в «Избранном».
Индексы: `(group_id, shared_at desc, review_id)` — лента группы; `(review_id)`.

#### Категория рекомендации
До этапа 8.2 категории принадлежали группам, и категория хранилась на публикации (`review_groups.category_id`); при публикации её нужно было выбирать для каждой группы, а при вступлении — сопоставлять по шаблону. ADR-011 заменил это общим набором: категория — поле рекомендации (`reviews.category_id`), одна во всех группах. Миграция V8 перенесла старые категории по шаблону V4 (`template_id` → ключ набора), остальным назначила «Без категории».

### saved_filters (сохранённые фильтры и закрепления, V9, этап 8.2.2)
| Поле | Тип | Примечание |
|---|---|---|

| user_id | uuid → users | on delete cascade; при мягком удалении аккаунта записи удаляет обработчик `UserDeleting` |
| kind | varchar(16) | `FILTER` — фильтр панели, `CATEGORY` — закреплённая корневая категория |
| name | varchar(60) | только у `FILTER` |
| category_id | uuid → categories | только у `CATEGORY`; частичный unique `(user_id, category_id) where kind = 'CATEGORY'` |

Форма записи каждого вида проверяется `CHECK`; лимит 50 записей на пользователя и порядок — в приложении под advisory-блокировкой пользователя.

### tags и review_tags
`tags(id bigint identity, name citext unique)` — общий словарь; «ё» в имени хранится как «е» (нормализация `Validation.normalizeTag`, V8 слила совпавшие теги); неиспользуемые теги удаляет ночная задача `TagCleanup` (этап 8.1, R12; запись тегов и чистка сериализуются advisory-блокировкой) — имя без `#`; в БД `CHECK (char_length(name) between 1 and 30)`, а формат (буквы и цифры Unicode, `_`, `-`) проверяет приложение (`Validation.tag`): класс `[[:alnum:]]` зависит от локали БД; `review_tags(review_id, tag_id)` PK обоих, индекс `(tag_id, review_id)`.
Теги группы = `DISTINCT` теги публикаций группы (запрос по индексам). При необходимости — материализованная таблица `group_tags` со счётчиками.

### Служебные таблицы
- `refresh_tokens(id, user_id, family_id, token_hash unique, device_info, session_started_at, created_at, expires_at, rotated_at, revoked_at)` — ротация и обнаружение повторного использования. `family_id` = сессия (устройство): у живой сессии ровно один не использованный и не отозванный токен; `session_started_at` переносится при ротации и ограничивает возраст сессии (90 дней). `created_at` живого токена = время последнего обновления.
- `email_codes(id, email citext, code_hmac bytea, created_at, expires_at, attempts, consumed_at, ip)` — одноразовые коды входа; пароля в системе нет. Активен всегда последний неиспользованный код email. Лимиты отправки считаются запросами к этой таблице (по email и по ip за час; интервал — по `max(created_at)`), операции с кодами одного email сериализуются `pg_advisory_xact_lock`. Записи удаляются по расписанию (старше суток). Индексы `(email, created_at desc)`, `(ip, created_at desc)`.
- `registrationToken` не хранится: это подписанный короткоживущий JWT.
- `mail_outbox(id, to_address, template, locale, payload jsonb, status, attempts, next_attempt_at, created_at, sent_at)` — `status`: `PENDING`/`SENT`/`FAILED`. Пока письмо не отправлено, в `payload` лежит одноразовый код в открытом виде (иначе его не отправить); после отправки или окончательной ошибки `payload` стирается (`{}`), обработанные записи удаляются через 7 дней. Выборка — `FOR UPDATE SKIP LOCKED`.
- `reports(id, reporter_id, target_type, target_id, reason, status, created_at)`; `user_blocks(blocker_id, blocked_id)` (этап 9).
- `flyway_schema_history` — Flyway.

## Поиск и фильтрация

- Полнотекстовый: `search_vector` + GIN-индекс, запрос `websearch_to_tsquery('russian', :q)`, ранжирование `ts_rank_cd`. Русская морфология обеспечивается словарём `russian` (snowball). Опционально — словарь `unaccent`.
- Нечёткий поиск по названию: GIN `title_search gin_trgm_ops` (опечатки, подстроки; до V7 — по `title`).
- «ё» и «е» не различаются (V7): нормализованы `search_vector`, `title_search` и сам запрос.
- Фильтры: категории (по `reviews.category_id`; корень включает подкатегории), теги (`ALL`/`ANY` — режим на согласование, по умолчанию `ALL`), автор. Все условия добавляются как параметры одного запроса к `review_groups` с ограничением по группам пользователя.
- Видимость: каждый запрос чтения содержит условие `review_groups.group_id IN (группы пользователя)`; для поиска по «всем моим группам» — подзапрос по `memberships`.
- Списки с этапа 8.2.2 (`FilterSql`): область — публикации в группах запроса, свёрнутые до строки на рекомендацию (`max(shared_at)`, `array_agg(group_id)`), поэтому на «Все» рекомендация одна (И15); для одной группы область читается по индексу ленты. Те же область и условия используют фасеты (`group by category_id`, по тегам, по авторам) и оглавление (`group by coalesce(parent_id, id)` — корневые секции; `count`, `max(shared_at)` для каждого закреплённого фильтра). Новых индексов не понадобилось: на 100 000 рекомендациях оглавление ≤ 50 мс, секция ≤ 55 мс, фасеты ≈ 75 мс, «Все» ≈ 85 мс (p95, `SearchPerformanceTest`).

Реализация (этап 7): индексы `reviews_search_idx` (GIN по `search_vector`, V5) и `reviews_title_trgm_idx` (GIN `gin_trgm_ops` по `title`, V6). Запрос совпадает, если сработал полнотекстовый поиск, подстрока (`ILIKE` с экранированием `%`, `_`, `\`) или триграммное сходство; релевантность = `ts_rank_cd + similarity(title, q)`. Категории с потомками — по `categories.parent_id` внутри запроса `reviews` (с этапа 8.2.1 таблица принадлежит модулю `reviews`). Замер на 100 000 рекомендациях (тест `SearchPerformanceTest`): лента ≈ 10 мс, поиск по тексту и опечаткам ≤ ≈ 110 мс, теги группы ≈ 80 мс (p95).

## Правила шаринга при вступлении (реализация)
Одна транзакция вступления: запрос отбирает групповые рекомендации автора по правилу (личные не переносятся), затем публикации вставляются пакетом `on conflict do nothing`. Вариативность (все / категории / теги / кроме...) строится в приложении из структуры правила; правило не хранится (разовое действие — открытый вопрос №5). Категория — на рекомендации, поэтому сопоставлять ничего не нужно (до этапа 8.2 — подбор по `template_id` и ручные назначения).

## Целостность и каскады
| Событие | Результат |
|---|---|
| Категория набора | Не удаляется: скрывается (`archived`) |
| Удаление группы | Каскад: роли, членства, приглашения, публикации. Отзывы только этой группы по выбору администратора: переходят в «Личное» авторов либо удаляются (с подтверждением); отзывы, опубликованные и в других группах, остаются; чужое «Избранное» чистится (Ф1) |
| Выход или исключение из группы | Удаление членства; при выходе по флагу — публикации автора в группе (не видные больше нигде переходят в «Личное»); чужое «Избранное» ушедшего чистится (Ф1) |
| Снятие публикации | Чужое «Избранное» чистится (Ф1) |
| Удаление отзыва | Каскад по `review_groups`, `review_tags` |
| Удаление аккаунта | Мягко: анонимизация `users`, удаление токенов, членств и системных групп; отзывы с публикациями в обычных группах по умолчанию переводятся на системного пользователя (`author_id`) и остаются в чужом «Избранном» (Ф2), личные удаляются; если пользователь выбрал «удалить все мои отзывы» — удаляются все его отзывы вместе с публикациями и тегами |
Отзывов без публикаций нет: личный отзыв опубликован в «Личном» автора (с V8; до этапа 8.2 личными считались отзывы без публикаций).

## Безопасность БД
- Приложение подключается ролью `podgon_app` (только DML, без DDL); миграции выполняет владелец схемы (`PODGON_DB_MIGRATOR_USER`). Роль и права по умолчанию на будущие таблицы создаёт `deploy/db-init/app-role.sql` (этап 8.1, R6; проверяется тестом `DbRolesTest`).
- Нет публичного доступа к порту БД; TLS-соединение.
- Только параметризованные запросы (защита от SQL-инъекций на уровне приложения); логирование медленных запросов.
- Бэкапы: ежедневные + PITR, регулярная проверка восстановления.
- Персональные данные: email и профиль в `users`; шифрование диска провайдером.
- Row Level Security — рассмотрено и **не включаем** на старте (усложняет пул соединений и миграции); защита реализована в приложении и тестах. Вернёмся при выделении сервисов.

## Индексы (стартовый набор)
- `users`: unique email (частичный), unique username.
- `memberships`: PK `(group_id, user_id)`, `(user_id)`.
- `groups`: частичный unique `(created_by, kind) where kind <> 'REGULAR'`.
- `categories`: unique `key`, `(parent_id)`.
- `review_groups`: см. выше.
- `reviews`: `(author_id, created_at desc)`, `(category_id)`, GIN(`search_vector`), GIN trgm(`title_search`).
- `refresh_tokens`: unique `token_hash`, `(user_id)`.

## Согласованность с остальными частями
Ограничения длин и форматов (username, displayName, bio, rating, теги) дублируются в OpenAPI-контракте, серверной валидации и клиентской форме; источник правды — контракт и `CHECK` в БД, расхождения ловятся тестами.
