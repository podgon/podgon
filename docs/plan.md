# План реализации

Следует процессу из description.md. Каждый этап включает вертикальный срез: **контракт API → БД (миграция) → сервер → клиент → тесты**, чтобы части системы менялись согласованно.

## Процесс этапа (чек-лист для каждого этапа)
1. Проверить, не повлияли ли изменения прошлых этапов на план этого; при необходимости скорректировать и согласовать.
2. Обновить контракт `api/openapi.yaml`, миграции БД.
3. Реализация (сервер, клиент) в ветке `feature/<этап>-...` от `develop`.
4. Тесты, ручное тестирование.
5. Code review, устранение замечаний, повторное тестирование.
6. Документирование кода (комментарии на русском), обновление `*.md`.
7. Merge в `develop`. Merge в `stable` — только через MR и по явному запросу разрешения; `main` — релиз через MR ревьюера.
8. Переход к следующему этапу.

## Этап 0. Согласование и подготовка
- Согласовать архитектуру и открытые вопросы (architecture.md §8), хостинг выбран — Selectel, антибот — Яндекс SmartCaptcha; выбрать почтового провайдера, завести аккаунты (Selectel, Google Play), проверить допустимость аккаунта Google Play на Узбекистан для резидента РФ, проверить доступность выбранных сервисов из РФ без VPN (ADR-010), оформить обработку ПДн по 152-ФЗ.
- Структура монорепозитория, защита веток `main`/`stable`, шаблон MR, CI-скелет, линтеры.
- **DoD:** открытые вопросы закрыты или явно отложены (отложены: почтовый провайдер, DDoS-защита и тариф Selectel, статус оператора ПДн, аккаунт Google Play — решаются в начале этапа 9); ветки защищены; CI зелёный на пустых проектах; решения оформлены ADR.

## Этап 1. Каркас бэкенда и БД
- Spring Boot проект, модули-пустышки, Spring Modulith-проверки, профили, конфигурация через env.
- PostgreSQL + Flyway, начальная миграция (расширения `citext`, `pg_trgm`), Testcontainers.
- Dockerfile, docker-compose (backend + Postgres + Mailpit), Actuator health, единый формат ошибок (RFC 9457 Problem Details), UTF-8 везде.
- **DoD:** `docker compose up` поднимает систему; `/actuator/health` = UP; интеграционный тест с реальным Postgres проходит в CI; миграции применяются с нуля.

## Этап 2. Пользователи и вход по коду (сервер)
- Вход/регистрация по одноразовому коду из письма (ADR-006): запрос кода, подтверждение, регистрация (username, displayName), refresh с ротацией, выход, сессии устройств, профиль (displayName, bio, username).
- Генерация и HMAC-хранение кодов, rate limit по email/IP, лимиты попыток и повторной отправки, интеграция CAPTCHA (SmartCaptcha), outbox писем, управляемый тестовый код для модерации магазинов (флаг).
- Общий модуль `shared-contract` (модели, валидация, коды ошибок).
- **DoD:** все сценарии покрыты интеграционными тестами, включая негативные (перебор кода, истёкший/использованный код, повторное использование refresh, спам запросами); код и токены не попадают в логи; ответ одинаков для существующего и несуществующего email; OpenAPI опубликован; ревью безопасности пройдено.

## Этап 3. Каркас KMP-клиента (Android) и вход
- KMP-проект (`commonMain` + `androidMain`), Compose Multiplatform, Material 3, навигация, DI (Koin), Ktor-клиент из OpenAPI, защищённое хранилище токенов (`expect/actual`), автообновление токена.
- Экраны: ввод email, ввод кода, регистрация (username/displayName), профиль и сессии. Локализация ru/en с самого начала.
- **DoD:** сквозной сценарий «email → код → регистрация → вход → выход» работает против сервера в docker-compose; unit-тесты ViewModel; нет cleartext-трафика; проект собирается и для iOS-таргета (проверка совместимости, без релиза).

## Этап 4. Группы, участники, роли, приглашения
- Создание группы (создатель = администратор), приглашения (email/ссылка), вступление, удаление участников, назначение администраторов, кастомные роли, инвариант «минимум один админ».
- Клиент: список групп, экран группы, участники, управление ролями, приглашения.
- **DoD:** права проверяются на сервере (тесты на чужие группы); инварианты защищены и ограничениями БД/транзакциями; сценарии работают в клиенте.
- **Решения этапа (сверка плана с состоянием после этапа 3):**
  - Приглашение — одноразовый/многоразовый код (120 бит, читаемый алфавит Crockford), в БД хэш; «ссылка» — код, который вводится в приложении («Вступить по коду»). Universal/App Links с доменом — этап 9–11, токен от этого не зависит. Адресное приглашение (email) отправляется письмом через outbox; принять его может только пользователь с этим email.
  - Правила шаринга при вступлении (`unmatched` и т.д.) требуют отзывов и категорий — реализуются на этапе 6 как расширение `POST /invitations/accept`; на этапе 4 вступление без переноса отзывов.
  - Удаление группы пока физическое (каскад; отзывов ещё нет), с `?confirm=true`; выбор судьбы отзывов и параметр `deleteMyReviews` при выходе — этап 6.
  - Права: не участник → 404 (существование не раскрываем), участник без роли админа → 403. Инвариант «≥ 1 админ» — блокировка строки группы `FOR UPDATE` в сервисе + отложенный constraint trigger в БД.
  - Лимиты (настраиваются): групп на пользователя 50, участников в группе 500, активных приглашений в группе 100, email-приглашений от одного пользователя 20 в час.
  - Модуль `groups` получает данные пользователей через публичный порт `identity.UserDirectory`, письма — через `mail.MailQueue`.

## Этап 5. Категории
- Базовый набор категорий (seed-шаблон), копирование в группу при создании, иерархия, создание/удаление администратором, предупреждения при удалении, правила удаления пустой категории / категории только с отзывами инициатора.
- Клиент: дерево категорий, диалоги подтверждения.
- **DoD:** корректные каскады; тест на глубокую иерархию и циклы (цикл запрещён); подтверждения в UI.
- **Решения этапа (сверка плана с состоянием после этапа 4):**
  - Новый модуль `catalog` (`app.podgon.catalog`); права через `groups.GroupAccess`: читать дерево может любой участник (`requireMember`), создавать/переименовывать/переносить/удалять — только админ (`requireAdmin`). Не участник → 404.
  - Миграция V4: `category_templates` + `category_template_translations` (ru/en, seed: Книги, Фильмы, Рестораны, Путешествия → Страны, Услуги…) и `categories` (составной FK родителя в той же группе, `unique (id, group_id)`, уникальность имени среди соседей без учёта регистра).
  - Копирование шаблона — в той же транзакции, что и создание группы (`GroupService.create`), через публичный порт `catalog.CategoryTemplates` (язык — `locale` создателя; нет перевода → `en`).
  - Иерархия — adjacency list; глубина ≤ 5 (настраивается в `CatalogProperties`), категорий на группу ≤ 500; цикл при переносе (`parentId` в собственном поддереве) → 409/400 с машинным кодом; проверка в сервисе под блокировкой строки группы + рекурсивный CTE.
  - Отзывов ещё нет (этап 6): `delete-impact` возвращает `subcategories` и `publications` (пока всегда 0); правило «удаляет только категорию, где все публикации принадлежат инициатору» подключается на этапе 6 вместе с `review_groups`. Удаление категории с подкатегориями (или публикациями) без `?confirm=true` → 400 `CONFIRMATION_REQUIRED` (как у групп); последствия клиент берёт из `GET .../delete-impact` до диалога.
  - Реализовано: перенос — `PUT .../categories/{id}/parent` (родитель `null` = корень); коды ошибок `CATEGORY_NAME_TAKEN`, `CATEGORY_CYCLE`, `CATEGORY_TOO_DEEP` (все 409); шаблон копируется обработчиком синхронного события `groups.GroupCreated` (модуль `catalog` зависит от `groups`, не наоборот — иначе цикл в Modulith); изменения дерева сериализуются `pg_advisory_xact_lock` на группу. Контракт 0.4.0.
  - Клиент: экран «Категории» в группе (дерево, добавление/переименование/удаление для админа), диалог подтверждения на основе `delete-impact`.

## Этап 6. Рекомендации
- CRUD рекомендаций (в том числе личных, без групп), оценка 1–10, теги, публикация в группы с категорией для каждой группы, лента группы с keyset-пагинацией.
- Клиент: лента, карточка, форма создания/редактирования (выбор групп/категорий/тегов), локальный кэш (Room).
- **DoD:** автор управляет только своим; участники видят только опубликованное в своих группах; нагрузочный smoke на ленту (индексы подтверждены `EXPLAIN`).
- **Решения этапа (сверка плана с состоянием после этапа 5):**
  - Срезы: **6a** сервер (контракт 0.5.0, миграция V5, модуль `reviews`), **6b** клиент (лента, карточка, форма), **6c** локальный кэш. Ветка `feature/stage6-reviews`, в `develop` — после всех срезов и ручной проверки.
  - Границы модулей: `reviews` зависит от `groups.GroupAccess` (добавляются `isMember` и `memberGroupIds`) и `identity.UserDirectory`; `catalog` зависит от нового порта `reviews.ReviewPublications` (подсчёт публикаций в наборе категорий) — обратной зависимости нет: корректность «категория принадлежит группе» гарантирует составной внешний ключ в БД, нарушение → 400/404.
  - Модель: `reviews` (название ≤ 200, описание ≤ 5000, оценка 1–10), `review_groups` (PK `(review_id, group_id)`, составной FK на категорию с `on delete cascade` — публикации удаляются вместе с категорией), `tags`/`review_tags` (теги до 10 на рекомендацию, ≤ 30 символов, `citext`; хранятся без `#`).
  - Права: создаёт и меняет рекомендацию только автор; публиковать можно только в группы, где автор состоит. Читать рекомендацию может автор и участник любой группы, где она опубликована; иначе 404. Личная рекомендация (без групп) видна только автору.
  - `PUT /reviews/{id}/groups` заменяет набор публикаций целиком; у сохраняющихся публикаций `shared_at` не меняется, у новых — текущее время.
  - Лента группы — keyset-пагинация по `(shared_at desc, review_id)`, курсор непрозрачный (base64), `limit` по умолчанию 20, максимум 50. Фильтры (категории, теги, автор, поиск) — этап 7; `GET /reviews?groupIds=` (лента по нескольким группам) — тоже этап 7.
  - Удаление категории (дополнение этапа 5): `delete-impact.publications` считается по поддереву; удалить может админ, если публикаций нет либо все они принадлежат инициатору, иначе 409 `CATEGORY_HAS_FOREIGN_REVIEWS`; публикации удаляются каскадом, сами рекомендации остаются.
  - Удаление группы пока каскадно снимает публикации (рекомендации остаются личными = вариант `RETURN_TO_PERSONAL`); выбор `DELETE`, `deleteMyReviews` при выходе и судьба публикаций ушедшего участника — этап 8 (в плане там же). Роль автора в карточке ленты — backlog (нужен порт ролей).
  - Клиент: кэш — Room KMP (проверено: совместим с Kotlin 2.4.21/KSP/AGP 9.4 на android + iOS; SQLDelight не понадобился). Кэшируются первые страницы лент и открытые карточки как JSON; офлайн — только чтение. Реализовано.

## Этап 7. Поиск и фильтры
- Полнотекстовый поиск (русская морфология) + trigram по названию; фильтры по категориям (с потомками), тегам, автору, их комбинации.
- Клиент: поиск, панель фильтров, сохранение последнего фильтра.
- **DoD:** релевантный поиск на тестовом наборе; фильтры комбинируются; производительность на ~100k рекомендаций приемлема (целевой p95 < 300 мс).
- **Решения этапа (сверка плана с состоянием после этапа 6):**
  - Срезы: **7a** сервер (контракт 0.6.0, миграция V6, поиск и фильтры), **7b** клиент (поиск, панель фильтров, сохранение последнего фильтра). Ветка `feature/stage7-search`; в `develop` — после ручной проверки на телефоне.
  - Единый запрос поиска по публикациям: `GET /groups/{id}/reviews` (одна группа) и новый `GET /reviews` (`groupIds=` — подмножество своих групп, без параметра — все свои; чужая группа → 404). Результат — публикации (рекомендация в группе), поэтому рекомендация в двух группах приходит двумя карточками; в `ReviewCard` добавляется `groupId`.
  - Фильтры (комбинируются через И): `categoryIds` — категория **с потомками** (рекурсивный CTE по таблице `categories`, чтение внутри SQL `reviews`, как и внешний ключ; иначе получился бы цикл модулей `catalog` ↔ `reviews`), `tags` + `tagMode=ALL|ANY` (по умолчанию `ALL`), `authorId`, `q`. Лимиты: `q` ≤ 100 символов, ≤ 20 категорий, ≤ 10 тегов, ≤ 50 групп.
  - Поиск `q`: совпадение, если полнотекстовое `websearch_to_tsquery('russian', q)` по `search_vector`, или подстрока в названии (`ILIKE`, триграммный GIN), или триграммное сходство названия (опечатки). Релевантность = `ts_rank_cd` + `similarity(title, q)`. С `q` выдача упорядочена по релевантности (затем по времени публикации), без `q` — по времени. Курсор — непрозрачный, его вид зависит от режима; курсор другого режима → 400.
  - Автодополнение и панель фильтров: `GET /groups/{id}/tags?prefix=` — теги группы с числом публикаций (до 100, по убыванию).
  - Клиент: строка поиска и панель фильтров в ленте группы; экран «Поиск» по всем своим группам (из списка групп); последний фильтр ленты группы запоминается в локальном кэше (ключ `filter:<groupId>`) и очищается при выходе.
  - Нагрузка: тест на ~100 000 публикаций проверяет планы запросов и время (целевой p95 < 300 мс).

## Этап 8. Шаринг при вступлении, выход из группы, удаление аккаунта
- Правила «поделиться»: все / категории / подкатегории / теги / кроме категорий / кроме тегов / ничего (с предпросмотром количества). Категория в новой группе подбирается по `template_id`; для записей без соответствия пользователь назначает категорию вручную или отказывается от их переноса.
- Выход из группы (опционально с удалением своих публикаций в ней; единственному админу запрещён), удаление группы с выбором судьбы отзывов, мягкое удаление аккаунта (анонимизация, отзыв токенов; отзывы либо переводятся на системного пользователя, либо удаляются по выбору пользователя), веб-страница удаления аккаунта для Google Play.
- **DoD:** все варианты правил покрыты тестами; выход/удаление не нарушают инварианты групп; данные удалённого пользователя недоступны.
- **Решения этапа (сверка плана с состоянием после этапа 7):**
  - Срезы: **8a** сервер: выход, удаление группы, шаринг при вступлении (контракт 0.7.0); **8b** сервер: удаление аккаунта и веб-страница; **8c** клиент. Ветка `feature/stage8-sharing`; в `develop` — после ручной проверки на телефоне.
  - Модули не получают обратных зависимостей: `groups` и `identity` публикуют **синхронные события** внутри своей транзакции (`MemberLeft`, `GroupDeleting`, `MemberJoining`, `UserDeleting`), `reviews` их обрабатывает. Эндпоинты, которым нужны данные отзывов (`GET /groups/{id}/delete-impact`, `GET /groups/{id}/leave-impact`, предпросмотр шаринга), живут в контроллере `reviews`.
  - Выход: `POST /groups/{id}/leave?deleteMyReviews=true` удаляет публикации автора в этой группе (рекомендация остаётся в других группах и в личных); без флага публикации остаются в группе. Единственный админ — 409 `LAST_ADMIN`, как и раньше.
  - Удаление группы: `DELETE /groups/{id}?confirm=true&reviews=RETURN_TO_PERSONAL|DELETE` (по умолчанию `RETURN_TO_PERSONAL`). `DELETE` удаляет рекомендации, опубликованные только в этой группе; опубликованные ещё где-то остаются. `GET /groups/{id}/delete-impact` — число таких рекомендаций и всех публикаций.
  - Шаринг при вступлении: правило `ShareRule` (`NONE`, `ALL`, `CATEGORIES`, `CATEGORIES_EXCEPT`, `TAGS`, `TAGS_EXCEPT`; флаг `withSubcategories`; категории — **исходные**, из групп пользователя). Рекомендации пользователя, ещё не опубликованные в новой группе, отбираются правилом по каждой исходной публикации (личные рекомендации без группы подходят только правилам `ALL`, `TAGS*`, `CATEGORIES_EXCEPT`). Категория в новой группе — по `template_id` исходной; без соответствия — `unmatched`.
  - `POST /invitations/share-preview` (токен + правило) → число отобранных, число с автоподбором, список `unmatched` (до 100), категории новой группы для ручного выбора; не меняет данных. `POST /invitations/accept` принимает тот же `share` и `assignments` (reviewId → categoryId); неразрешённые без назначения не переносятся (= отказ). Всё в одной транзакции вместе с членством, дубликаты исключены ключом `(review_id, group_id)`.
  - Удаление аккаунта: подтверждение кодом из письма — `POST /me/deletion/code` (код на email пользователя, шаблон `ACCOUNT_DELETION_CODE`, те же лимиты, что и у входа) и `POST /me/deletion` (`code`, `deleteReviews`); `GET /me/delete-impact` — число рекомендаций, из них опубликованных, и группы, где пользователь единственный админ. Единственный админ группы с другими участниками → 409 `LAST_ADMIN` (передать права или удалить группу); единственный участник — группа удаляется. Далее: `reviews` переводят рекомендации с публикациями на системного пользователя, личные без публикаций и (при `deleteReviews`) все — удаляют; затем анонимизация `users`, отзыв токенов, удаление кодов.
  - Веб-страница для Google Play: статическая `/account-deletion` (ru/en) с инструкцией и тем, какие данные удаляются; самообслуживание без приложения (форма с капчей) — этап 9 вместе с виджетом SmartCaptcha.

## Этап 8.1. Замечания по review первых 8 этапов

## Этап 9. Модерация и подготовка к публикации
- **Сначала закрыть отложенные вопросы:** выбрать почтового провайдера, уточнить DDoS-защиту и тариф managed PostgreSQL в Selectel, оформить статус оператора ПДн (юрист, политика обработки), проверить аккаунт Google Play на Узбекистан для резидента РФ. До этого этапа разработка и тестирование идут локально (docker-compose, Mailpit, заглушки CAPTCHA и почты).
- Хостинг (`docs/hosting.md`): до этапа 9 — стенд на домашнем NAS в локальной сети (Х1); перед публикацией — внешняя VPS с Caddy и WireGuard-туннелем до NAS (Х2), бэкапы вне дома.
- Жалобы на контент/пользователей, блокировка пользователя, политика конфиденциальности и условия использования.
- Публикация в **Google Play** (аккаунт на Узбекистан): R8/ProGuard, подписание, Data safety форма, политика конфиденциальности, иконки/скриншоты, закрытое тестирование; запасной канал — APK с сайта. Финальные лимиты антибота.
- Проверка работы приложения из РФ без VPN на реальных устройствах и сетях разных операторов.
- **DoD:** приложение прошло предрелизную проверку Google Play; полный сценарий работает из РФ без VPN; security-review пройден.

## Backlog (после первой версии)
Push-уведомления (FCM), фото в рекомендациях, лайки/комментарии, избранное, второй фактор, вынос поиска в отдельный сервис.
Из редизайна клиента (`docs/design.md`; в прототипе кнопки есть, но ничего не делают):
- Уведомления в приложении (колокольчик) с настройкой, о чём уведомлять: подписка на фильтр (новые рекомендации
  по нему), приглашения, комментарии к своим рекомендациям (комментарии — тоже backlog); позже push.
- Аватары пользователей: загрузка, хранение файлов, ограничения размера, модерация (сейчас у всех аватар по умолчанию).
- Пользовательские категории группы (вариант К-Б, `docs/design.md`): админ создаёт подкатегорию набора с подсказкой существующих; кнопка «нет нужной категории».
- Список входящих приглашений в группы в приложении (сейчас — только письмо с кодом).
- Подписки на сохранённые фильтры (уведомления о новых рекомендациях; сами фильтры — этап 8.2).
- Фото в рекомендациях (загрузка, хранение, превью, модерация).
