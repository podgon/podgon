# Архитектура Podgon

Документ описывает общую архитектуру системы, ключевые решения (ADR), сквозные аспекты (безопасность, развёртывание, качество) и открытые вопросы.
Детали подсистем: [client.md](client.md), [server.md](server.md), [db.md](db.md). План работ: [plan.md](plan.md).

## 1. Контекст и цели

Podgon — мобильное приложение для обмена рекомендациями внутри закрытых групп. Ключевая ценность — доверие: пользователь видит только то, чем поделились участники его групп.

Архитектурные драйверы:

| Драйвер | Следствие |
|---|---|
| Закрытость данных (видимость только внутри групп) | Проверка прав на сервере в каждом запросе, единая точка авторизации доступа к данным, тесты на утечки между группами |
| Старт монолитом, возможный переход к микросервисам | Модульный монолит с жёсткими границами модулей |
| Запуск в контейнере | Stateless-бэкенд, конфигурация через переменные окружения, 12-factor |
| Публикация в Google Play (позже App Store) | Целевой SDK, подписанные AAB, политика удаления аккаунта, privacy policy; логика отделена от UI для возможного KMP |
| Бесплатные стабильные библиотеки | Только mainstream OSS (Spring, Compose, PostgreSQL и т. п.) |
| Защита от ботов, DDoS, SQL-инъекций, перебора паролей | Многоуровневая защита (раздел 6) |
| Русский язык в артефактах и комментариях, UTF-8 везде | Фиксируем в конфигурации БД, JVM, HTTP, сборки |

## 2. Общая схема

```
┌──────────────────────┐        HTTPS (REST/JSON, JWT)        ┌─────────────────────────────┐
│ Android-приложение   │ ───────────────────────────────────▶ │ CDN/WAF/Reverse proxy       │
│ Kotlin + Compose     │                                       │ (TLS, rate limit, anti-bot) │
│ Room (кэш)           │ ◀─────────────────────────────────── │                             │
└──────────────────────┘                                       └──────────────┬──────────────┘
                                                                              ▼
                                                               ┌─────────────────────────────┐
                                                               │ Backend (Spring Boot, Java) │
                                                               │ модульный монолит, контейнер│
                                                               └──────┬───────────────┬──────┘
                                                                      │ JDBC          │ SMTP / API
                                                                      ▼               ▼
                                                            ┌────────────────┐  ┌────────────────┐
                                                            │ PostgreSQL     │  │ Почтовый       │
                                                            │ (Flyway-миграц.)│  │ провайдер      │
                                                            └────────────────┘  └────────────────┘
```

Клиент не имеет прямого доступа к БД: только через API бэкенда. БД доступна только из приватной сети бэкенда.

## 3. Ключевые решения (ADR)

### ADR-001. Модульный монолит
- **Решение:** один деплоймент, внутри — модули с публичным API и скрытой реализацией (`identity`, `groups`, `catalog` (категории), `reviews`, `search`, `notifications`/`mail`).
- **Обоснование:** требование описания. Модульный монолит дешевле в разработке и эксплуатации, чем микросервисы, но при жёстких границах позволяет вынести модуль позже.
- **Как обеспечиваем границы:** Spring Modulith (проверка зависимостей тестами), общение модулей только через интерфейсы пакета `api` и доменные события; нет JOIN-ов и FK между таблицами разных модулей, кроме идентификаторов (см. db.md — допущение: FK внутри одной БД оставляем ради целостности, но запросы пересекают границы только через сервисы).
- **Альтернатива:** сразу микросервисы — отвергнуто (YAGNI, сложность для команды).

### ADR-002. Backend: Java 21 LTS + Spring Boot 3.x
- **Обоснование:** требование (Java, LTS); Spring Boot — де-факто стандарт, зрелые Security, Data, Validation, Actuator; Java 21 даёт виртуальные потоки и records.
- **Альтернативы:** Quarkus/Micronaut (быстрый старт, меньше памяти, но меньше опыта и материалов); Kotlin на сервере (единый язык с клиентом, но в описании указан Java-стек). Рекомендация: **Spring Boot на Java 21**. Переход на Java 25 LTS — отдельной задачей после стабилизации экосистемы.
- **Сборка:** Gradle (Kotlin DSL) — единый инструмент с Android; допустим Maven, если команде привычнее.

### ADR-003. БД: PostgreSQL 16+
- **Обоснование:** бесплатная, производительная, зрелая; нативные возможности, нужные проекту: полнотекстовый поиск (русская морфология), `pg_trgm`, рекурсивные CTE для иерархии категорий, частичные индексы, `citext`, JSONB.
- **Миграции:** Flyway (версионированный SQL, принцип «БД меняется только миграциями»).
- **Поиск:** на первом этапе — встроенный FTS PostgreSQL, без Elasticsearch (YAGNI). Выделение поиска в отдельный модуль даст возможность заменить движок.

### ADR-004. Клиент: Android, Kotlin, Jetpack Compose
- **Обоснование:** современный стандарт Google; Compose + ViewModel + Coroutines/Flow — рекомендуемая архитектура (Guide to app architecture).
- **Альтернативы:** Kotlin Multiplatform + Compose Multiplatform для iOS. Рекомендация: **на старте чистый Android**, но domain/data-слои писать без Android-зависимостей (чистые Kotlin-модули), чтобы позже вынести в KMP-модуль без переписывания.

### ADR-005. Протокол: REST/JSON, контракт OpenAPI (contract-first)
- **Обоснование:** простота, поддержка инструментов, кэширование. Единый контракт `openapi.yaml` в репозитории — источник правды для клиента и сервера, что выполняет принцип «изменения согласованы и не противоречат друг другу».
- Из контракта генерируются DTO/интерфейсы (openapi-generator) для сервера и клиента; в CI проверка обратной совместимости (например, `oasdiff`).
- **Альтернативы:** GraphQL (избыточно для текущих сценариев), gRPC (хуже для мобильного/отладки). Версионирование через префикс `/api/v1`.

### ADR-006. Аутентификация: email + пароль, подтверждение email, JWT access + rotating refresh
- **Регистрация:** email + имя пользователя + пароль → письмо с одноразовым кодом/ссылкой (TTL 15 мин, хранится только хэш) → аккаунт активируется. Без подтверждения вход невозможен.
- **Пароль:** Argon2id (Spring Security `Argon2PasswordEncoder`), политика длины ≥ 10, проверка по списку утёкших паролей (опционально, k-anonymity HIBP).
- **Токены:** access JWT (15 мин, подпись EdDSA/RS256 или HS256 с ротацией ключа), refresh — непрозрачный случайный токен, в БД только хэш, ротация при каждом использовании, обнаружение повторного использования → отзыв всей цепочки (token family). На клиенте хранение в `EncryptedSharedPreferences`/Keystore.
- **Альтернативы:** серверные сессии (проще отзыв, но хуже для мобильных клиентов и горизонтального масштабирования); OAuth/Google Sign-In (удобно, но требование — email с подтверждением; можно добавить позже); passwordless (magic link/OTP) — рассмотреть как вариант улучшения UX, но в описании явно есть смена пароля, поэтому базово — пароль.
- **Перехват учётных данных:** только TLS 1.2+, HSTS; на клиенте network-security-config без cleartext; опционально certificate pinning (с осторожностью из-за ротации сертификатов — через pin на промежуточный/резервные ключи).

### ADR-007. Модель видимости: «рекомендация + публикация в группу»
- Рекомендация принадлежит автору; доступ к ней группе даёт запись «публикации» (`review_group`). Эта связь many-to-many хранит также **категорию рекомендации в рамках этой группы** (категории принадлежат группам, а рекомендация может быть в нескольких группах — прямая ссылка на одну категорию невозможна).
- Выход из группы с удалением отзывов = удаление записей публикаций этого автора в данной группе; сама рекомендация остаётся в других группах.
- Правило безопасности: любой запрос чтения рекомендаций обязан идти через представление «доступные пользователю публикации» (join по членству). Реализуется в одном месте (репозиторий/спецификация), покрывается тестами.
- Подробности и альтернативы: db.md, раздел «Категория рекомендации».

### ADR-008. Мягкое удаление пользователей
- Учётная запись помечается `deleted_at`, email освобождается/анонимизируется (хэш), персональные данные очищаются; отзывы остаются или удаляются — **открытый вопрос** (см. §8). Требование Google Play: возможность удаления аккаунта внутри приложения и по веб-ссылке.

### ADR-009. Уведомления и почта
- Отправка писем через абстракцию `MailSender`; в разработке — Mailpit/MailHog, в проде — SMTP/API провайдера (Mailgun, Postmark, Amazon SES, Yandex Cloud Postbox). Отправка асинхронная (outbox-таблица, повтор при сбоях).
- Push (FCM) — вне первой версии, но модуль `notifications` оставляем под него.

## 4. Структура репозитория

```
podgon/
├── api/            openapi.yaml — контракт
├── server/         Spring Boot (Gradle)
├── android/        Android-приложение (Gradle, мультимодульное)
├── db/             справочные материалы: ER-диаграмма, seed; миграции живут в server/
├── deploy/         Dockerfile, docker-compose, манифесты
├── docs/adr/       отдельные ADR по мере появления
└── *.md            описание, архитектура, план
```
Монорепозиторий упрощает согласованность контракта между частями (единый MR меняет API, сервер и клиент).

## 5. Ветвление, CI/CD, качество

- Ветки: `main` (production), `stable` (production-ready), `develop` (разработка). Фичи — `feature/<этап>-<кратко>` от `develop`.
- Push в `main` и `stable` только через MR, принимает человек-ревьюер (защищённые ветки в GitHub). Merge в `stable` — только по явному запросу разрешения.
- CI (GitHub Actions): сборка, unit-/integration-тесты (Testcontainers с PostgreSQL), статанализ (Checkstyle/Spotless, Detekt/ktlint), проверка контракта OpenAPI, сканирование зависимостей (Dependabot, OWASP dependency-check), сборка Docker-образа.
- Тестовая пирамида: unit → интеграционные (API + реальный Postgres в контейнере) → UI-тесты ключевых сценариев на клиенте.
- Соглашения: Java — Google Java Style (Spotless), Kotlin — официальный Kotlin style (ktlint), SQL — snake_case, комментарии и документация на русском.
- Наблюдаемость: структурированные логи (JSON), Actuator health/metrics, Prometheus-совместимые метрики, трассировка запросов через `X-Request-Id`; без персональных данных в логах.

## 6. Безопасность (сквозные меры)

| Угроза | Меры |
|---|---|
| Доступ без авторизации | Все эндпоинты, кроме `/auth/*` и health, закрыты; deny-by-default в Spring Security |
| Перебор пароля / credential stuffing | Rate limit по IP и по логину (Bucket4j + хранилище в памяти/Redis), экспоненциальная задержка и временная блокировка после N неудач, единое сообщение об ошибке (без раскрытия существования email) |
| Автоматическая регистрация | Лимиты по IP/устройству/домену email, CAPTCHA (Cloudflare Turnstile / hCaptcha / Google reCAPTCHA / Play Integrity API на Android), подтверждение email, запрет одноразовых доменов (опционально), для закрытой группы — вход **по приглашению** как дополнительный фильтр |
| DDoS | CDN/WAF перед бэкендом (Cloudflare, Yandex Cloud Smart Web Security, AWS Shield — выбирает хостинг), лимиты размера запроса и таймауты |
| SQL-инъекции | Только параметризованные запросы (JPA/Spring Data/jOOQ), запрет конкатенации SQL, отдельный пользователь БД с минимальными правами, статанализ |
| Перехват данных | TLS, HSTS, нет cleartext на клиенте |
| Хранение пароля | Argon2id с солью и параметрами, настраиваемыми через конфигурацию |
| Утечка данных между группами | Единая точка проверки членства, интеграционные тесты «чужая группа» → 404/403 |
| IDOR | Идентификаторы UUID + обязательная проверка прав на ресурс |
| XSS/инъекции в тексте отзывов | Текст хранится как plain text; клиент рендерит без HTML; на сервере валидация длины и нормализация |
| Секреты | Только в переменных окружения/секрет-хранилище, не в репозитории |
| Прямой доступ к БД | БД в приватной сети, нет публичного порта, роль приложения без DDL |

**Варианты защиты от ботов (для решения на этапе 0):**
1. WAF/CDN хостинга + rate limit на уровне прокси (минимум, бесплатно/дёшево).
2. + CAPTCHA на регистрации и восстановлении пароля (Turnstile — бесплатно, privacy-friendly).
3. + Play Integrity API (подтверждает, что запрос идёт от настоящего приложения из Google Play).
4. + регистрация только по инвайту. **Рекомендация:** 1 + 2 на старте, 3 — перед публикацией, 4 — как опция группы.

## 7. Развёртывание

- Образ бэкенда: multi-stage Dockerfile, non-root, слои Spring Boot (layered jar), healthcheck.
- Локально: `docker-compose` (backend + PostgreSQL + Mailpit).
- Прод: контейнерная платформа по выбору (VPS + compose / Kubernetes / Cloud Run / Yandex Cloud Serverless Containers) + управляемый PostgreSQL с бэкапами (PITR). Для первой версии рекомендуется самый простой вариант: один VPS/контейнерный сервис + managed PostgreSQL.
- Окружения: `dev` (develop), `stage` (stable), `prod` (main).
- Миграции Flyway выполняются при старте (для одного инстанса) либо отдельной задачей деплоя (при нескольких).

## 8. Предложения по дополнению описания и открытые вопросы

Предложения (требуют согласования):
1. **Единый реестр категорий группы + «базовый набор» как шаблон:** при создании группы шаблон копируется в категории группы (отслеживается `template_id` для сопоставления между группами).
2. **Приглашения:** по email или по ссылке/коду с TTL и лимитом использований; принятие приглашения — только авторизованным пользователем.
3. **Теги:** нормализуются (нижний регистр, без пробелов, `#` — только в UI), общий словарь тегов; «теги группы» = теги, использованные в публикациях группы. Это проще, чем отдельные теги на группу, и удовлетворяет фильтрации.
4. **Оценка 1–10**, целая; выводить среднее по названию не требуется (YAGNI).
5. **Лайки/комментарии, избранное, «хочу попробовать»** — вне первой версии (backlog).
6. **Модерация:** жалоба на отзыв/пользователя — для публикации в Google Play (UGC-политика) нужна возможность пожаловаться и заблокировать контент/пользователя. **Включить в план** (этап 8).
7. **Фото в рекомендациях** — backlog (потребует объектное хранилище S3-совместимое).

Открытые вопросы:
1. При удалении учётной записи отзывы удалять или оставлять анонимизированными?
2. Может ли рекомендация существовать без групп (черновик/личная)? Предложение: да, как «личная», видимая только автору.
3. При создании новой рекомендации автоматически ли публиковать в группы, куда автор уже вступил? Предложение: нет, пользователь выбирает группы явно (с запоминанием последнего выбора).
4. Как определять категорию рекомендации при публикации в несколько групп, если в группах разные деревья категорий? Предложение: пользователь выбирает категорию для каждой группы; по умолчанию подставляется категория с тем же `template_id`.
5. Правила «поделиться при вступлении» — разовое действие или постоянное правило (авто-публикация будущих отзывов)? Предложение: разовое.
6. Нужен ли «владелец» группы отдельно от администраторов? Предложение: нет, достаточно требования «минимум один администратор».
7. Пользователь, покидающий группу единственным администратором: запретить выход или автоматически назначать? Предложение: запретить, пока не назначен другой админ или группа не удалена.
8. Можно ли удалить группу? Предложение: да, администратором, с подтверждением, физически каскадом по публикациям (сами рекомендации остаются).
9. Уникальность имени пользователя: регистронезависимая? Предложение: да (`citext`), допустимые символы `[a-z0-9_.]`, 3–30.
10. Хостинг и юрисдикция (влияет на выбор WAF, почтового провайдера, требования по хранению ПДн).
11. Требуется ли офлайн-режим на клиенте? Предложение: чтение закэшированного — да, создание в офлайне — нет (YAGNI).
12. Языки интерфейса: только русский на старте? Строки выносим в ресурсы сразу.
